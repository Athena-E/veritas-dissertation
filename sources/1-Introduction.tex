\chapter{Introduction}\label{ch:intro}

\section{Motivation}

In his 1977 paper, Leslie Lamport defined \emph{safety} as a property ensuring that ``something bad never happens'' \cite{Lamport1977Proving}. In systems programming, \emph{memory safety} translates to a guarantee: no out-of-bounds reads, no null-pointer dereferences, and no other memory-related \emph{undefined behaviour} (UB). In C and C++, it is the programmer's responsibility to uphold these guarantees, and failures can be severe: Heartbleed (2014) \cite{CVE-2014-0160} was an unchecked bounds error that leaked sensitive memory. This motivates \emph{executable-level memory safety} without relying only on programmer discipline. The central question of this dissertation is not only whether source programs can be checked for memory safety, but where the trust boundary should lie once those programs have been compiled.

% TODO: improvement on C/C++
One approach, exemplified by languages such as Rust, is to enforce safety properties at the source level. This offers an attractive combination of performance and safety, but still trusts a large and evolving compiler to preserve those frontend guarantees during compilation. If a compiler bug miscompiles a safe source program, the resulting executable may no longer preserve the guarantee that was checked at the frontend.

A second approach is \emph{verified compilers}: compilers whose correctness is justified using formal methods. CompCert \cite{compcert}, a compiler for a subset of C written in Rocq \cite{RocqRefman}, provides a guarantee of \emph{semantic preservation} and reduces the \emph{Trusted Computing Base} (TCB) from the entire compiler to just Rocq's kernel. However, since CompCert compiles C, semantic preservation does not by itself make unsafe source programs safe: memory safety remains a property the programmer must establish.

Taken together, these approaches point toward a compiler for a safety-enforcing source language whose correctness is itself verified: source-level memory safety, plus semantic preservation through compilation. Verifying such a compiler, however, comes at the cost of writing and maintaining thousands of lines of machine-checked mathematical proofs.

\emph{Proof-carrying code} (PCC) \cite{Necula1997PCC} offers a way to move this trust boundary down to the compiled artifact without verifying the compiler itself: the producer of low-level code also ships evidence that the code obeys a safety policy, and the consumer checks this evidence before execution. One way to realise this idea is \emph{type-preserving compilation}, where type information is preserved from the source language down to assembly. A low-level type system can then encode the relevant safety properties, leaving only the verifier trusted for memory safety. % The idea is to reduce the size of the trusted computing base from a large compiler into a much smaller checker. % Notably, it is possible to independently verify the type safety and memory safety of DTAL code via a type-checker.

The gap addressed by this dissertation is the lack of a small, executable systems-language toolchain that combines source-level refinement checking with independently checkable low-level output, without requiring a fully verified compiler.

This dissertation presents \textbf{Veritas}, a small systems-language toolchain that applies PCC-style low-level checking to a refinement-typed source language. Its pipeline is:

\begin{center}
\begin{tcolorbox}[colback=white,colframe=black!70,width=0.86\textwidth,boxrule=0.5pt]
\centering
\textbf{Veritas source} $\rightarrow$ typed SSA $\rightarrow$ DTAL $\rightarrow$ independent verifier $\rightarrow$ executable
\end{tcolorbox}
\end{center}

The target language is a version of Dependently Typed Assembly Language (DTAL), inspired by Xi and Harper \cite{Xi2001DTAL}. The central claim is not that the compiler is correct, but that source-level refinement guarantees are carried into untrusted low-level output and re-checked before execution. This reduces the TCB from the compiler pipeline to the standalone verifier and its dependencies.


\section{Approach and aims}

Veritas consists of four core components.

\keyblock[0pt]{The Veritas Language}{A systems language with refinement types, loop invariants, and function contracts. These annotations give programmers a way to state the source-level safety facts that must survive compilation.}

\keyblock{Dependently Typed Assembly Language}{A target language based on Xi and Harper's DTAL \cite{Xi2001DTAL} that embeds type states and constraints into the instruction stream. DTAL is the low-level artifact checked by the verifier, so it must make the relevant safety evidence explicit.}

\keyblock{Type-preserving compiler pipeline}{A pipeline that lowers source programs through typed SSA (Static Single Assignment) to DTAL while preserving safety invariants. The compiler is not trusted for correctness; its output is accepted only if the verifier can check it.}

\keyblock{DTAL verifier}{A tool that checks DTAL programs without access to the source code. This is the main trust-boundary shift: the final safety decision is made by the verifier rather than by the compiler pipeline.}

% Veritas focuses on structural guarantees rather than semantic correctness: a program may still compute the wrong result, but it should not violate the required memory and control-flow invariants. To express and discharge these guarantees, Veritas uses refinement types \cite{Rondon2008Liquid}, which decorate ordinary types with logical predicates. For example, a natural number may be typed not just as \texttt{int}, but as $\{v : \mathtt{int} \mid v \ge 0\}$ i.e. a value of type \texttt{int} such that the value is greater than or equal to zero. Programmers provide specifications at key boundaries through type annotations, preconditions, postconditions, and loop invariants, while the compiler discharges the resulting proof obligations using an SMT solver. The preserved specifications in the target code are checked by the verifier at the DTAL level using the same approach. Veritas also synthesises refinements for intermediate arithmetic expressions, allowing the system to preserve precise facts about computed values as they move from source code to assembly.

Together, these components support the core question of the dissertation: whether a small systems-language toolchain can realise the trust model suggested by proof-carrying code, with an untrusted compiler whose low-level output is independently checked before execution. The dissertation evaluates this along two main axes:

\begin{samepage}
\keyblock[0pt]{Trust architecture}{Whether the relevant low-level safety properties of compiled programs can be checked independently at the DTAL level, whether DTAL can express the safety properties in scope, and whether the verifier remains small enough to audit without access to the source code or compiler state.}

\keyblock{Expressiveness and practicality}{Whether the source language supports realistic imperative, systems-oriented programs while retaining automatic verification.}
\end{samepage}
