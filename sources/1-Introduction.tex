\chapter{Introduction}\label{ch:intro}

In his seminal 1977 paper, Leslie Lamport defined \emph{safety} as a property ensuring that ``something bad never happens'' \cite{Lamport1977Proving}. In systems programming, where code written in languages such as C and C++ often runs with elevated privileges, \emph{memory safety} translates to a guarantee: no out-of-bounds reads, no null-pointer dereferences, and no other memory-related undefined behaviour (UB). Yet, the history of systems software demonstrates the difficulty of achieving such guarantees in practice. The Heartbleed bug \cite{CVE-2014-0160} was ultimately an unchecked bounds error that leaked sensitive memory contents, and the Code Red worm exploited a buffer overflow in Microsoft's Internet Information Services (IIS) to compromise 359,000 servers in less than 14 hours \cite{Microsoft2001MS01-033}.

The Heartbleed bug \cite{CVE-2014-0160} was ultimately an unchecked bounds error that leaked sensitive memory contents, and the Therac-25 accidents \cite{Leveson1993AnIO} demonstrate how failures in software structure can have severe real-world consequences. In each case, the problem was not merely that the program computed an incorrect result, but that it violated a more basic safety property.

Modern languages and toolchains address this problem in different ways, but they tend to place trust in one of two locations. At one extreme are languages such as Rust, which use safety-oriented features such as the borrow checker to enforce compile-time memory safety. This offers an attractive combination of performance and safety, but requires trusting that an enormous and evolving compiler will correctly preserve the guarantees established by the source-level type system. At the other extreme are \emph{verified compilers}: compilers that use formal methods to verify the correctness of the compilation process. One widely known example is CompCert \cite{compcert}: a compiler for a subset of C written in Coq \cite{CoqRefman}, an interactive theorem prover. While this provides a guarantee of \emph{semantic preservation}, the cost of developing and modifying such a compiler involves writing thousands of lines of machine-checked mathematical proofs, the majority of which do not contribute to the actual compilation process; in the initial prototype of the compiler backend, the Coq functions representing the compiler itself accounted for only 13\% of the codebase \cite{Xavier2006CompCert}.

In PCC, the producer of some low-level code also ships evidence that the code obeys a chosen safety policy, and the consumer checks this evidence before execution. The key idea is to move trust away from a large compiler and into a much smaller checker: instead of trusting that compilation was performed correctly, one checks a proof, certificate, or other machine-checkable witness attached to the compiled program. One way to realise this idea is through \emph{type-preserving compilation}, where the compiler retains rich type information all the way to a low-level target language. In this project, that target is a dependently typed assembly language inspired by Xi and Harper's DTAL \cite{Xi2001DTAL}, in which registers, memory values, and control-flow join points are annotated with types and logical constraints. The resulting low-level program can then be re-checked independently of the compiler that produced it.

The idea is to reduce the size of the trusted computing base from a large compiler into a much smaller checker. The work of Xi and Harper features a \emph{Dependently Typed Assembly Language} (DTAL) \cite{Xi2001DTAL}, designed as the target for a type-preserving compilation pipeline in which registers, memory values, and control-flow join points are annotated with types and logical constraints. Notably, it is possible to independently verify the type safety and memory safety of DTAL code via a type-checker.

This dissertation presents \textbf{Veritas}, a toolchain that attempts to address the compromise between performance and safety by applying ideas behind PCC. Veritas compiles source programs for a small systems language to a version of DTAL (inspired by Xi and Harper), and then uses a standalone verifier to re-prove the safety properties encoded in the low-level program.

The central trust-model claim of Veritas is not that the compiler is correct, but that an untrusted compiler can still produce code whose structural safety is checked independently before execution. Veritas focuses on structural guarantees rather than full semantic correctness: a program may still compute the wrong result, but it should not violate the memory and control-flow invariants captured by its types.

To express and discharge these guarantees, Veritas uses refinement types \cite{Rondon2008Liquid}, which decorate ordinary types with logical predicates. For example, a value may be typed not just as \texttt{int}, but as $\{v : \mathtt{int} \mid v \ge 0\}$. Programmers provide specifications at key boundaries through type annotations, preconditions, postconditions, and loop invariants, while the compiler discharges the resulting proof obligations using an SMT solver, which are checked by the verifier at the DTAL level using the same underlying SMT approach. Veritas also synthesises refinements for intermediate arithmetic expressions, allowing the system to preserve precise facts about computed values as they move from source code to assembly.

\section{Aims and Contributions}

The aim of this project is to deliver a type-preserving compilation pipeline that supports independent verification of code for a small systems language. The key contributions are:

% TODO: add runtime and unikernel?
\begin{itemize}
  \item \textbf{The Veritas Language:} a systems language featuring refinement types, loop invariants, and function contracts.
  \item \textbf{Type-Preserving Backend:} a pipeline that lowers high-level types to a typed SSA (Static Single Assignment) intermediate representation, preserving all defined safety invariants.
  \item \textbf{x86 runtime generation:} an assembler that maps DTAL instructions to x86 and generates an executable ELF.
  \item \textbf{Dependently Typed Assembly Language (DTAL):} a target language based on Xi and Harper \cite{Xi2001DTAL} that embeds type states and constraints directly into the instruction stream.
  \item \textbf{Independent Verifier:} a tool that re-verifies DTAL programs without access to the source code, reducing the trusted computing base to the verifier and the SMT solver.
  \item \textbf{Formal Evaluation:} a suite of programs used to measure the overhead and expressiveness of the architecture.
\end{itemize}
