\chapter{Introduction}\label{ch:intro}

In his seminal 1977 paper, Leslie Lamport defined \emph{safety} as a property ensuring that ``something bad never happens'' \cite{Lamport1977Proving}. In systems programming, where code written in languages such as C and C++, often runs with elevated privileges, \emph{memory safety} translates to a guarantee: no out-of-bounds reads, no null-pointer dereferences, and no other memory-related undefined behaviour (UB). Yet, the history of systems software demonstrate the difficulty of achieving such guarantees in practice. The Heartbleed bug \cite{CVE-2014-0160} was ultimately an unchecked bounds error that leaked sensitive memory contents, and the Therac-25 accidents \cite{Leveson1993AnIO} demonstrate how failures in software structure can have severe real-world consequences.

The Heartbleed bug \cite{CVE-2014-0160} was ultimately an unchecked bounds error that leaked sensitive memory contents, and the Therac-25 accidents \cite{Leveson1993AnIO} demonstrate how failures in software structure can have severe real-world consequences. In each case, the problem was not merely that the program computed an incorrect result, but that it violated a more basic safety property.

Modern languages and toolchains address this problem in different ways, but they tend to place trust in one of two locations. At one extreme are languages such as Rust, which use strong static checks, including ownership and borrow checking, to reject broad classes of undefined behaviour before execution. This offers an attractive combination of performance and safety, but only under the assumption that the compiler correctly preserves the guarantees established by the source-level type system. At the other extreme are \emph{verified compilers} such as CompCert \cite{compcert}.
% A verified compiler is not merely well tested; rather, its implementation is accompanied by a machine-checked proof that each compilation stage preserves the meaning of the source program, so the generated target code is correct with respect to a formal semantics. These systems provide very strong guarantees, but they are difficult to build, maintain, and extend, particularly when targeting expressive source languages and practical low-level backends.

Veritas explores a third position based on \emph{Proof-Carrying Code} (PCC) \cite{Necula1997PCC}. In PCC, the producer of some low-level code also ships evidence that the code obeys a chosen safety policy, and the consumer checks this evidence before execution. The key idea is to move trust away from a large compiler and into a much smaller checker: instead of trusting that compilation was performed correctly, one checks a proof, certificate, or other machine-checkable witness attached to the compiled program. One way to realise this idea is through \emph{type-preserving compilation}, where the compiler retains rich type information all the way to a low-level target language. In this project, that target is a dependently typed assembly language inspired by Xi and Harper's DTAL \cite{Xi2001DTAL}, in which registers, memory values, and control-flow join points are annotated with types and logical constraints. The resulting low-level program can then be re-checked independently of the compiler that produced it.

This dissertation presents \textbf{Veritas}, a toolchain that applies this idea to a small systems language with refinement types, function contracts, and loop invariants. Veritas compiles source programs through a typed SSA-based intermediate representation to DTAL, and then uses a standalone verifier to re-prove the safety properties encoded in the generated low-level program. The central trust-model claim is therefore not that the compiler is correct, but that an untrusted compiler can still produce code whose structural safety is checked independently before execution. Veritas focuses on these structural guarantees rather than full semantic correctness: a program may still compute the wrong result, but it should not violate the memory and control-flow invariants captured by its types.

To express and discharge these guarantees, Veritas uses refinement types \cite{Rondon2008Liquid}, which decorate ordinary types with logical predicates. For example, a value may be typed not just as \texttt{int}, but as $\{v : \mathtt{int} \mid v \ge 0\}$. Programmers provide specifications at key boundaries through type annotations, preconditions, postconditions, and loop invariants, while the compiler and verifier discharge the resulting proof obligations using the Z3 SMT solver \cite{DeMoura2008Z3}. Veritas also synthesises refinements for intermediate arithmetic expressions, allowing the system to preserve precise facts about computed values as they move from source code to assembly.

\section{Aims and Contributions}

The aim of this project is to deliver a type-preserving compilation pipeline that supports independent verification of systems code. The key contributions are:

% TODO: add runtime and unikernel?
\begin{itemize}
  \item \textbf{The Veritas Language:} A systems language featuring refinement types, loop invariants, and function contracts.
  \item \textbf{Type-Preserving Backend:} A pipeline that lowers high-level types to a typed SSA (Static Single Assignment) intermediate representation, preserving all defined safety invariants.
  \item \textbf{x86 runtime generation:} An assembler that maps DTAL instructions to x86 and generates an executable ELF.
  \item \textbf{Dependently Typed Assembly (DTAL):} A target language based on Xi and Harper \cite{Xi2001DTAL} that embeds type states and constraints directly into the instruction stream.
  \item \textbf{Independent Verifier:} A tool that re-verifies DTAL programs without access to the source code, reducing the trusted computing base to the verifier and the SMT solver.
  \item \textbf{Formal Evaluation:} A suite of programs used to measure the overhead and expressiveness of the architecture.
\end{itemize}
