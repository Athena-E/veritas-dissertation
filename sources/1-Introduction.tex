\chapter{Introduction}\label{ch:intro}

\section{Motivation}

In his 1977 paper, Leslie Lamport defined \emph{safety} as a property ensuring that ``something bad never happens'' \cite{Lamport1977Proving}. In systems programming, \emph{memory safety} translates to a guarantee: no out-of-bounds reads, no null-pointer dereferences, and no other memory-related \emph{undefined behaviour} (UB). In C and C++, it is the \emph{programmer's} responsibility to uphold these guarantees, and failures to do so can have severe consequences: Heartbleed (2014) \cite{CVE-2014-0160} was ultimately an unchecked bounds error that leaked sensitive memory. So, given (inevitable) human infallibility, what are the available strategies to mitigate, or even eliminate, memory safety bugs in systems programming?

% TODO: improvement on C/C++
One approach, exemplified by languages such as Rust, is to enforce \emph{safety properties at the source level} using mechanisms such as the borrow checker. This offers an attractive combination of performance and safety, but we must trust that a large and evolving compiler preserves these frontend guarantees during compilation. If a compiler bug miscompiles a safe source program, the resulting executable may no longer preserve the guarantee that was checked at the frontend.

A second approach is \emph{verified compilers}: compilers whose correctness are justified using formal methods. CompCert \cite{compcert}, a compiler written in Rocq for a subset of C \cite{RocqRefman}, provides a guarantee of \emph{semantic preservation} and reduces the \emph{Trust Computing Base} (TCB) from the entire compiler to Rocq's relatively smaller kernel. However, since CompCert compiles is C, responsibility is still placed on the programmer to uphold memory safety.

One might suggest combining the previous two methods: a verified compiler for a safety-enforcing source language. Verifying such a compiler, however, comes at the cost of writing and maintaining thousands of lines of machine-checked mathematical proofs.

\section{Moving the trust boundary: Proof-Carrying Code}

\emph{Proof-carrying code} (PCC) \cite{Necula1997PCC} offers a way to move the trust boundary down to the compiled artifact without verifying the compiler itself: the producer of low-level code also ships evidence that the code obeys a safety policy, and the consumer checks this evidence before execution. One way to realise this idea is \emph{type-preserving compilation}, where types carrying information about memory safety properties are preserved from the source language down to assembly. In the abstract PCC model, the typed low-level artefact can be checked by a \emph{verifier}; in a concrete implementation, the TCB would consist of just the verifier (and its dependencies).

\section{A practical middle-ground: Veritas}

The gap addressed by this dissertation is the lack of a small, executable systems-language toolchain that combines source-level refinement checking with independently checkable low-level output, without requiring a fully verified compiler.

This dissertation presents \textbf{Veritas}, a toolchain that applies the ideas behind PCC to compile source programs for a small systems language to a version of a Dependently Typed Assembly Language (DTAL) \cite{Xi2001DTAL}. In the supported fragment, Veritas checks: fixed-size array bounds, function preconditions and postconditions, block-entry type-state compatibility, selected arithmetic side conditions, and ownership/borrow-state consistency. Claims that are \emph{out-of-scope} include: full source-to-target semantic preservation, full memory safety in the sense of arbitrary heap and pointer behaviour, correctness of Z3, correctness of the final encoder/runtime, or full Rust-like borrow checking. The central claim is not that the compiler is correct. Rather, the compiler emits low-level output carrying enough type and constraint information for an independent verifier to check a scoped low-level safety policy before execution. This moves much of the compiler pipeline outside the TCB for that policy, while still trusting the verifier and its dependencies.

\section{Approach and Aims}

Veritas consists of four main components:

\begin{itemize}
  \item \textbf{The Veritas Language:} a systems language featuring refinement types, loop invariants, and function contracts.
  \item \textbf{Dependently Typed Assembly Language (DTAL):} a target language based on Xi and Harper's DTAL \cite{Xi2001DTAL} that embeds type states and constraints directly into the instruction stream.
  \item \textbf{Type-Preserving Compiler Pipeline:} a pipeline that lowers high-level types to a typed SSA (Static Single Assignment) typed intermediate representation to DTAL, preserving the safety invariants that I define in the requirements analysis (Section~\ref{sec:requirements-anal}).
  \item \textbf{DTAL Verifier:} a tool that checks DTAL programs for compliance with memory safety properties without access to the source code, reducing the trusted computing base to the verifier and its dependencies.
\end{itemize}

Together, these components support the core question of the dissertation: whether a small systems-language toolchain can realise the trust model suggested by proof-carrying code, with an untrusted compiler whose low-level output is independently checked before execution. The dissertation evaluates this along two main axes:
\begin{itemize}
  \item \textbf{Trust architecture:} Veritas should demonstrate that the relevant low-level safety properties of compiled programs can be checked independently at the DTAL level. The design of DTAL for Veritas should be able to express the safety properties in scope. The verifier should also be substantially small than the full compiler to reduce the risk of trusting it.
  \item \textbf{Expressive source language:} the source language should be expressive enough both from a verification perspective as well as from a systems-language perspective, by remaining suitable for safety verification, and realistic imperative, systems-oriented programs.
  \item \textbf{Practicality:} the overall toolchain should remain usable in practice, by keeping the compiler performance and additional cost of independent verification acceptable for a systems language toolchain.
\end{itemize}
