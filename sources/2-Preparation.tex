\chapter{Preparation}\label{ch:prep}

This chapter gives the background needed to understand Veritas: the type-system machinery used to express safety properties, related verification systems, and engineering decisions fixing the trust boundary. It establishes the theory and design context for the implementation.

\section{Background}\label{sec:background}

\subsection{Type systems and safety}

The fundamental theorem that connects type systems to safety is \emph{type soundness}: a well-typed program cannot `go wrong' at runtime~\cite{Milner1978Theory}. Wright and Felleisen formalised this via the \emph{progress} and \emph{preservation} lemmas~\cite{Wright1994Syntactic}:

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!75!black]
  \paragraph{Progress.} If $\emptyset \vdash e : \tau$, then either $e$ is already a value, or there exists some expression $e'$ such that $e \to e'$. \\

  \paragraph{Preservation.} If $\emptyset \vdash e : \tau$ and $e \to e'$, then $\emptyset \vdash e' : \tau$.
\end{tcolorbox}

% \textbf{Progress.} If $\emptyset \vdash e : \tau$, then either $e$ is already a value, or there exists some expression $e'$ such that $e \to e'$.
%
% \textbf{Preservation.} If $\emptyset \vdash e : \tau$ and $e \to e'$, then $\emptyset \vdash e' : \tau$.

% \noindent Progress states that a closed well-typed program never becomes stuck before it has produced a value: whenever evaluation has not yet finished, there is always a valid next reduction step. Preservation states that evaluation does not invalidate typing: every execution step preserves the type established statically. 
\noindent Starting from a well-typed program, repeated evaluation can neither get stuck in an ill-defined intermediate state (progress) nor escape the guarantees expressed by its type (preservation). This is the formal basis for claims such as ``a well-typed array access cannot go out of bounds'' or ``a well-typed arithmetic expression is not applied to a boolean''.

% An important consequence of tractability is that type systems are \emph{sound} but not \emph{complete}: every accepted program is safe, but some safe programs will be rejected. This is a deliberate trade-off---soundness is essential for guarantees, while completeness is sacrificed for decidability. Refinement types push this boundary by encoding richer invariants, but the fundamental incompleteness remains.

Type systems exist on an expressiveness spectrum. At one end, simply typed languages such as C distinguish broad categories like integers, floats, and pointers. This catches type mismatches---such as passing a pointer where an integer is expected---but cannot constrain inhabitants of a type. Hindley--Milner systems~\cite{Milner1978Theory}, used in ML and Haskell, add parametric polymorphism and principal type inference, enabling inference of the most general type for every expression without annotations. However, these systems cannot express value-dependent properties, such as an array index being within bounds or a division denominator being non-zero. Such safety-critical properties require types that can refer to values: \emph{dependent types} \cite{MARTINLOF1982153}.

\subsection{Dependent types and refinement types}\label{sec:dependent-types}

In a dependently typed language, types may depend on values. The canonical example is the type of vectors indexed by their length:

\[
  \begin{aligned}
    \textsf{Vec}    & : \textsf{Set} \rightarrow \mathbb{N} \rightarrow \textsf{Set} \\
    \textsf{Fin}    & : \mathbb{N} \rightarrow \textsf{Set}                          \\
    \textsf{lookup} & : \forall A,n.\;
    \textsf{Vec}(A,n)
    \to \textsf{Fin}(n)
    \to A
  \end{aligned}
\]

\noindent The type $\textsf{Vec}(A,n)$ corresponds to sequences of $A$ of length $n$ and $\textsf{Fin}(n)$ to numbers less than $n$. The function \textsf{lookup} returns the vector element at a specified index. Its type signature requires the index to be within the vector's length, statically eliminating out-of-bounds accesses.

Full dependent type systems, such as Rocq and Agda~\cite{Bove2009Agda}, can express arbitrary higher-order propositions as types (via Curry--Howard), but this generality is costly: type checking is expensive and may require explicit proof terms.

Refinement types~\cite{Rondon2008Liquid} are a decidable subset of dependent pairs:
\[
  \{v : \mathtt{int} \mid P(v)\} \simeq (v : \mathtt{int}) \times P(v)
\]
They are a practical restriction of full dependent types in which a base type is decorated with a logical predicate. For example, $\{v\!:\!\mathtt{int} \mid v > 0\}$ classifies strictly positive integers. Notably, subtyping between refinement types reduces to logical implication:
\[
  \{v\!:\!\mathtt{int} \mid P(v)\} <: \{v\!:\!\mathtt{int} \mid Q(v)\} \text{ holds when } P(v) \Rightarrow Q(v) \text{ is valid}
\]
% $\{v\!:\!\mathtt{int} \mid P(v)\} <: \{v\!:\!\mathtt{int} \mid Q(v)\}$ holds when $P(v) \Rightarrow Q(v)$ is valid. 
Because the predicates are drawn from a decidable theory (typically quantifier-free linear arithmetic), this implication check can be delegated to an SMT solver.

A useful special case is the singleton type, written $\mathtt{int}(n)$, inhabited only by integer $n$. Singleton types arise naturally from Xi and Pfenning's Dependent ML~\cite{Xi1999DML}, where integer index expressions track array sizes and loop bounds. They can propagate exact values through arithmetic:
\[
  \begin{array}{rcl}
    x     & : & \mathtt{int}(3) \\
    y     & : & \mathtt{int}(5) \\
    x + y & : & \mathtt{int}(8)
  \end{array}
\]
This enables compile-time verification of array bounds when indices are statically known.

\subsection{Bidirectional type checking}

Bidirectional type checking~\cite{Pierce2000Local} structures a type system into two mutually recursive judgements:

\begin{tcolorbox}[colback=blue!5!white,colframe=blue!75!black]
  \textsc{Type checking} takes a context $\Gamma$, program $e$ and type $\tau$ as input and produces a true/false output reflecting whether $e$ is well-typed: $\Gamma \vdash e \leftarrow \tau$. \\

  \textsc{Type synthesis} takes a context $\Gamma$ and program $e$ as input and produces a types $\tau$ as output: $\Gamma \vdash e \Rightarrow \tau$.
\end{tcolorbox}
% \begin{itemize}
%   \item \emph{Type checking} takes a context $\Gamma$, program $e$ and type $\tau$ as input and produces a true/false output reflecting whether $e$ is well-typed: $\Gamma \vdash e \leftarrow \tau$
%   \item \emph{Type synthesis} takes a context $\Gamma$ and program $e$ as input and produces a types $\tau$ as output: $\Gamma \vdash e \Rightarrow \tau$
% \end{itemize}

\noindent The two modes are connected by a subsumption rule:
$$
  \frac{\Gamma \vdash e \Rightarrow \sigma \quad \sigma <: \tau}{\Gamma \vdash e \leftarrow \tau}
$$
% \noindent To check an expression against a type $\tau$, one may synthesise a type $\sigma$ and then verify $\sigma$ is a subtype of $\tau$.

% type synthesis ($\Gamma \vdash e \Rightarrow \tau$), which infers the type of an expression bottom-up, and type checking ($\Gamma \vdash e \Leftarrow \tau$), which verifies that an expression has a given type top-down. The two modes are connected by a subsumption rule; to check an expression against a type $\tau$, one may synthesise a type $\sigma$ and then verify $\sigma <: \tau$.

% Alternative approaches have significant drawbacks. Full type inference in the style of Hindley--Milner requires unification, which does not extend naturally to subtyping or refinement types; the lattice structure of refinement types means there is no unique principal type for many expressions. At the other extreme, requiring complete type annotations on every expression is impractical. Bidirectional checking offers a middle ground where the programmer annotates introduction forms (function signatures, let-bindings) and the system infers the rest.

\noindent For refinement types, the bidirectional structure is particularly well-suited. Synthesis produces the most precise type available from an expression's immediate structure---for integer literals, a singleton type; for arithmetic, a refinement capturing the exact relationship between result and operands. Checking then verifies subtyping against the expected type. The programmer annotates only function boundaries and mutable variable declarations; the type checker infers intermediate refinement types automatically. Bidirectional type-checking sits between Hindley-Milner full inference and complete expression annotations.

% In Veritas, the bidirectional structure also threads the typing context through the judgements. Both synthesis and checking accept a context and return an updated context, reflecting changes from mutable variable assignments and newly learned refinement propositions.

\subsection{SMT-based verification}
\label{sec:smt-based-ver}

% Satisfiability Modulo Theories are an extension of boolean satisfiability (SAT) to richer logics. An SMT solver decides the satisfiability of first-order formulae over a combination of background theories. Theories relevant to program verification include linear integer arithmetic, boolean logic, bounded quantifiers, array theory, and uninterpreted functions.

The technique for using an SMT solver as a refinement type checker is \textit{proof by refutation}~\cite{Rondon2008Liquid}. Figure~\ref{fig:smt-refutation} shows the stages for checking whether a proposition $P$ follows from the set of known assumptions $\phi$.

This makes proof-obligation \textit{discharge} fully automatic: the programmer never constructs proof terms. However, the programmer still supplies the specifications that generate these obligations. The automation lies in checking, not specification.

\subsection{Proof-carrying code and typed low-level targets}\label{sec:pcc-background}

Proof-carrying code~\cite{Necula1997PCC} and typed assembly languages~\cite{Morrisett1999SystemF} establish the low-level trust argument used by Veritas. Instead of treating compilation as the point where types disappear, a certifying compiler emits code with enough evidence for a consumer-side checker to validate a safety policy. In a type-preserving compiler, that evidence is a low-level program annotated with types rich enough for an independent checker to reconstruct the safety argument. Veritas adopts this route: the compiler emits evidence, but the verifier trusts it only after re-deriving the relevant low-level facts.


\subsection{Dependently Typed Assembly}\label{sec:dtal-background}

Xi and Harper introduced DTAL as a target for type-preserving compilation from DML \cite{Xi1999DML} and Xanadu \cite{Xi2000Xanadu}, a dependently typed imperative programming language with C-like syntax. DTAL augments a conventional assembly language with two key forms of type annotation:
\begin{itemize}
  \item \textbf{Label signatures}: each basic block entry point is annotated with existentially quantified index variables and the types expected for each register on entry, enabling modular, block-by-block verification.
  \item \textbf{Register types}: types may depend on index variables, so that a register's type tracks its exact value (e.g., $\mathtt{int}(i)$) or the size of an array it points to (e.g., $\mathtt{int\;array}(n)$).
\end{itemize}

Figure~\ref{fig:copy-loop} shows the loop header of a DTAL copy function. The label signature binds index variables $m$, $n$, $i$ and declares register types in terms of them.

\begin{figure}[h]
  \begin{verbatim}
  loop:  {m:nat, n:nat | m <= n, i:nat}
         [r1: int array(m), r2: int array(n), r3: int(m), r4: int(i)]
         sub   r5, r4, r3       // r5 <- i - m
         bgte  r5, finish       // if i >= m, exit
         load  r5, r1(r4)       // safe: i < m
         store r2(r4), r5       // safe: i < n (since m <= n)
         add   r4, r4, 1
         jmp   loop
\end{verbatim}
  \caption{Loop header of a DTAL copy function.}
  \label{fig:copy-loop}
\end{figure}

The branch \texttt{bgte r5, finish} refines the type state: on the fall-through path, the type system knows $i < m$, which makes the subsequent \texttt{load} and \texttt{store} provably safe without any runtime bounds check.

\section{Related work and design influences}
\label{sec:related-work}

The design of Veritas synthesises several established approaches to software verification: automated refinement checking, systems-language design, and proof-carrying code.

\subsection{Refinement Types and Automated Verification}
Liquid Haskell~\cite{Vazou2014Refinement} and Liquid Types~\cite{Rondon2008Liquid} provide the main precedent for SMT-backed refinement checking. Dafny~\cite{Leino2010Dafny} similarly uses SMT solving for imperative contracts and loop invariants. Veritas adapts this automatic proof discharge, but carries the resulting constraints into assembly rather than erasing them after source-level verification.

\subsection{Foundational and Dependent Verification}
At the more expressive end are systems such as F*~\cite{Swamy2016Dependent}, which supports full dependent types, and RefinedC~\cite{Sammler2021RefinedC}, which applies refinement and ownership types to C code to enable machine-checked Coq proofs. Veritas chooses an automated SMT-backed foundation rather than foundational proof, trading proof-assistant generality for automatic checking in the compiled artifact once specifications are supplied.

\subsection{Verifiable Systems Languages}
The most direct predecessor to Veritas's goals is ATS (Applied Type System)~\cite{Xi2003Applied}. It targets systems programming using dependent types with zero runtime overhead. The key difference is architectural. ATS proves properties at compile time and emits C, leaving the ATS and C compilers in the TCB. Veritas instead preserves types into DTAL so the low-level target can be checked independently.

Together, these systems leave a specific gap. Liquid Haskell and Dafny show usable SMT-backed specifications, but their guarantees are principally source-level. F*, RefinedC, Coq, and Agda show stronger foundational assurance with heavier proof burden. TAL, PCC, and DTAL show how low-level artifacts can carry checkable evidence, but not the executable refinement-oriented source toolchain evaluated here. ATS shows dependent types supporting systems programming, but leaves the C backend in the trust boundary. Veritas targets the remaining point: automatic refinement checking in a systems-language fragment whose safety evidence is preserved into an independently checkable low-level artifact.

In compiler-assurance terms, Veritas occupies a design point close to certifying and type-preserving compilation, rather than whole-compiler verification. Its distinguishing choice is to carry refinement-derived evidence into an executable physical-register artifact and then validate that artifact independently. This makes register allocation, spill insertion, calling-convention lowering, and target-specific expansion visible to the checker instead of treating them as trusted consequences of a compiler proof.

\section{Design decisions}\label{sec:design-decisions}

This section applies the preceding theory to the language and trust model. These design choices share one goal: preserve enough semantic evidence through compilation for the final low-level artifact to be checked without trusting the compiler pipeline. That evidence also supports later optimisation: exact values, bounds, and refinement constraints remain available to backend passes instead of being erased after frontend checking.

\subsection{Trust model and TCB reduction}

To maintain a clear trust boundary during incremental implementation, I structured the implementation to move the verification boundary progressively lower in the pipeline:

\begin{enumerate}
  \item \textbf{Virtual V-DTAL verification}: the verifier checks V-DTAL with virtual registers. The TCB includes the verifier, Z3, register allocation, instruction selection, and the x86-64 encoder, ELF generator, and runtime assumptions.
  \item \textbf{Physical V-DTAL verification}: the verifier checks DTAL \textit{after} register allocation. Register allocation, spill insertion, and instruction selection are removed from the TCB. The TCB includes the verifier, Z3, a direct encoder, ELF generator, and runtime assumptions.
  \item \textbf{Runtime and bare-metal}: the runtime remains audit-sized, and a bare-metal target removes the OS kernel from the normal execution path. The TCB includes the bootstrap, runtime, hardware model, and emulator.
\end{enumerate}

\subsection{Source language design}

The Veritas source language has C-like imperative syntax focused on first-order array programs with local mutation and structured loops. The type system extends simple types with singleton types, refinement types, function contracts with bounded quantifiers, and loop invariants.

A key expressiveness choice was bounded quantification. Scalar refinements can prove facts about individual values, but algorithms such as binary search need array-wide properties such as sortedness. A precondition such as $\mathbf{forall}\ i\ \mathbf{in}\ 0..n\ \{\ \mathit{arr}[i] \le \mathit{arr}[i + 1]\ \}$ expresses such properties while avoiding unbounded quantification.

Supporting mutation also required care: refinements about a variable may become invalid after assignment. Veritas gives mutable bindings both a fixed master type and a current refinable type, so reassignment is checked against the master declaration while path-sensitive facts remain locally usable.

\subsection{V-DTAL design}
The target V-DTAL is a variant of Xi and Harper's DTAL~\cite{Xi2001DTAL}, extended for Veritas' refinement type system and targeting a RISC-like x86-64 subset. Simple instructions are easier to type and verify, and map naturally from the compiler’s SSA-style intermediate representation. V-DTAL is augmented with register type annotations, embedded constraint assertions, and declared type states at basic block entries.

I also defined a V-DTAL \textit{physical register model} that maps directly to x86-64 registers. This allows verification \textit{after} register allocation: the allocator is untrusted and its output verified before final x86-64 encoding.

\subsection{Machine code encoding and ELF generation}

Veritas encodes x86-64 instructions directly as bytes. The trusted path below physically-allocated V-DTAL is auditably direct: each V-DTAL instruction translates to exactly one x86-64 instruction, or a small fixed prologue/epilogue sequence, making the path amenable to manual audit.

The x86-64 target was pragmatic: the development machine runs x86-64 Linux, enabling direct execution and testing without emulation. Targeting another ISA would require replacing only instruction mapping, byte encoding, and register definitions, while leaving the V-DTAL type system and verifier structure largely unchanged.

\subsection{Verification via SMT}

The Veritas constraint system delegates frontend type checking and low-level verification to an SMT solver. The supported safety obligations are naturally expressed as arithmetic and logical implications over program values, and SMT-solving discharges them automatically without manual proofs for routine constraints.

In Veritas, the SMT solver is invoked at several points:
\begin{itemize}
  \item subtyping checks between refinement types (where the solver verifies that one predicate implies another);
  \item array bounds verification (where the solver must prove that an index lies within $[0, N)$);
  \item function contract verification (where preconditions and postconditions are checked at call sites and return points respectively).
\end{itemize}

Quantified array properties fall outside the decidable quantifier-free fragment of linear integer arithmetic, so the language restricts quantifiers to bounded forms. Because the SMT solver is in the TCB, solver risk must be minimised, and using an obscure solver would weaken this argument. Z3~\cite{DeMoura2008Z3}, developed by Microsoft Research, is one of the most widely used SMT solvers; I chose it for maturity and reliability. Z3 also natively supports the theories featured in Veritas (Section~\ref{sec:smt-based-ver}).

% For quantified specifications such as $\forall i \in [0, n).\; \mathit{arr}[i] \ge 0$, the translation uses Z3's built-in quantifier support: $\forall i.\; (0 \le i \wedge i < n) \Rightarrow \mathit{arr}[i] \ge 0$, where the array is represented as a Z3 array sort. Existential quantifiers are handled dually, asserting $\exists i.\; (a \le i \wedge i < b) \wedge P$. While quantified formulae move outside the decidable fragment of LIA, Z3's E-matching and model-based quantifier instantiation heuristics handle the bounded quantifiers that arise in practice effectively.

\section{Software engineering methodology}
\label{sec:software-eng-methodology}

\subsection{Methodology}

\paragraph{Development process.} Initial planning resembled a waterfall model for defining compiler pipeline modules, source and target language features, and specifications. Development then followed a spiral approach: the pipeline was built end-to-end for integer arithmetic, then extended with arrays, mutable variables, refinement types, function contracts, and quantifiers. Work items were planned in two-week Jira sprints. Each feature had positive tests that should compile and negative tests that should be rejected with a specific error.

\paragraph{Version control.} Version control used Git with trunk-based development and short-lived feature branches merged into main. A GitHub Actions CI pipeline ran on each push to maintain continuous correctness.

\paragraph{Code quality and testing.} The CI pipeline enforced formatting and linting with \texttt{cargo fmt} and \texttt{cargo clippy}. It also validated example programs and ran the test suite on Ubuntu Linux and macOS, covering the main systems development platforms and different Z3/libc environments. The test suite has unit tests for each significant module and integration tests between pipeline components.
\paragraph{Documentation.} I wrote module-level Rust doc comments and generated crate documentation using \texttt{cargo doc --open}.

The project integrated normally separate areas: dependent typing, refinement checking, SMT, compiler construction, x86-64 encoding, bidirectional type checking, and typed assembly.
