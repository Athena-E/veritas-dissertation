\chapter{Conclusion}\label{ch:conclusion}

This dissertation developed independently checkable low-level safety evidence for systems programs without trusting a full compiler or building a fully verified one. Veritas moves part of the trust boundary below the frontend: the compiler may remain untrusted for the checked DTAL safety policy if the emitted low-level artifact carries enough independently checkable information. The project implemented this architecture end to end: a refinement-typed imperative source language, verifier-facing compiler pipeline, DTAL-inspired low-level target, independent verifier, bare-metal target, and borrowing/ownership model. The system preserves contracts, array-bounds obligations, arithmetic side conditions, and ownership information through lowering, re-derives them at the physical-DTAL level, and still produces executable systems artifacts.

The main significance of Veritas is architectural. Source-level verification systems typically discharge obligations before compilation and then rely on the compiler stack; verified compilers provide end-to-end assurance but require substantial mechanisation. Veritas demonstrates a third point: an ordinary compiler pipeline can remain untrusted for a defined safety policy if it emits enough low-level evidence for an independent checker to re-derive the relevant facts after lowering. The physical-DTAL validation stage is central because register allocation, calling-convention lowering, spill insertion, and target-specific expansion are visible to the verifier rather than hidden inside the trusted compiler boundary.

The evaluation substantiates that design: the source language expresses non-trivial array, arithmetic, contract, invariant, quantifier, and ownership properties; compiled artifacts pass independent physical-DTAL verification; invalid source programs and tampered low-level artifacts are rejected. Preserved evidence also supports a performance trajectory: bounds, singleton values, and refinement constraints remain available to backend passes, and PolyBench shows competitive behaviour on lighter kernels before mature optimisation. Type preservation is therefore both the checking mechanism and the engineering lever for future performance.

\section{Future work}

\begin{itemize}
  \item \textbf{Richer source-language fragment.} The clearest extension is broader systems-programming idioms, including non-lexical lifetimes, reborrowing, richer heap-allocated data structures, and more expressive aliasing patterns.
  \item \textbf{Broader verified property classes.} Future versions can generalise the current array-bounds, arithmetic, contract, and ownership evidence to concurrency properties, information-flow policies, and cryptographic correctness or side-channel-oriented specifications.
  \item \textbf{Type-directed optimisation.} The backend can exploit the same facts that make verification possible to drive bounds-check elimination, constant propagation, alias-sensitive load fusion, and layout-aware code generation without weakening the trust architecture.
  \item \textbf{Verifier formalisation.} A longer-term assurance goal is to formalise the verifier or its core metatheory in a proof assistant, turning the current empirical checker evidence into a machine-checked soundness result.
\end{itemize}

\section{Reflections}
Veritas required sustained integration of programming-language theory, compiler construction, low-level code generation, and verifier engineering. The main lesson was that type-system decisions are architectural decisions: changing a source-language rule affected the TIR, DTAL representation, verifier, code generator, tests, and debugging workflow. The practices that mattered most were regression tests, reproducible benchmarks, small failure cases, and repeated review against the trust-architecture claim. Presenting the project outside the immediate supervision context sharpened the exposition of the trust model and motivation for a broader technical audience. The result is an end-to-end demonstration that type-system design can determine not only source-level checking, but also the trusted boundary and optimisation surface of the generated artifact.
