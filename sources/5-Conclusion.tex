\chapter{Conclusion}\label{ch:conclusion}

This dissertation developed independently checkable low-level safety evidence for systems programs without trusting a full compiler or building a fully verified one. Veritas moves part of the trust boundary below the frontend: the compiler may remain untrusted for the checked DTAL safety policy if the emitted low-level artifact carries enough independently checkable information. The project implemented this architecture end to end: a refinement-typed imperative source language, verifier-facing compiler pipeline, DTAL-inspired low-level target, independent verifier, bare-metal execution targets, and borrowing/ownership model. The system preserves safety-relevant facts such as contracts, array-bounds obligations, arithmetic side conditions, and ownership information through lowering and re-checks them at the low level, while remaining practical as a systems-language toolchain.

The main significance of Veritas is architectural. Source-level verification systems typically discharge obligations before compilation and then rely on the compiler stack; verified compilers provide end-to-end assurance but require substantial mechanisation. Veritas demonstrates a third point: an ordinary compiler pipeline can remain untrusted for a defined safety policy if it emits enough low-level evidence for an independent checker to re-derive the relevant facts after lowering. The physical-DTAL stage is central because register allocation, calling-convention lowering, spill insertion, and target-specific expansion are visible to the verifier rather than hidden inside the trusted compiler boundary.

\section{Future work}

\begin{itemize}
  \item \textbf{Richer source-language fragment.} The clearest extension is broader systems-programming idioms, including non-lexical lifetimes, reborrowing, richer heap-allocated data structures, and more expressive aliasing patterns.
  \item \textbf{Broader verified property classes.} Future versions can generalise the current array-bounds, arithmetic, contract, and ownership evidence to concurrency properties, information-flow policies, and cryptographic correctness or side-channel-oriented specifications.
  \item \textbf{Type-directed optimisation.} The backend can exploit the same facts that make verification possible, such as bounds, singleton values, and refinement constraints, to improve generated code without weakening the trust architecture. The runtime results identify this natural next step: preserved evidence is both a checking mechanism and an optimisation resource.
  \item \textbf{Verifier formalisation.} A longer-term assurance goal is to formalise the verifier or its core metatheory in a proof assistant, reducing implementation trust.

\section{Reflections}
Veritas is by far the largest and longest-running software project I have undertaken, requiring integration of programming-language theory, compiler construction, low-level code generation, and verifier engineering in one implementation. The main takeaway was that source-language or type-system decisions quickly affected the DTAL representation, verifier, code generator, and debugging workflow. I would keep the engineering practices that made the project manageable: regular testing, reproducible benchmarks, small regression cases, and frequent review against the trust-architecture claim. Discussing the project with others, including through regular standups and presenting a poster at the OxBridge Women in Computer Science Conference 2026\footnote{See \url{https://www.cs.ox.ac.uk/event/52-full.html}}, sharpened the exposition of the trust model and motivation for a diverse audience.
