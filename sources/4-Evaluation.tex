\paragraph{Feature suite.}

I wrote a suite of 28 programs covering all main program features: arrays, mutable state, references and borrowing, preconditions, loop invariants, quantifiers, sortedness reasoning, safe division, and overflow-aware arithmetic. Its purpose is to evaluate the compiler and verifier's performance and functional correctness on representative source-language features and proof obligations.

\paragraph{PolyBench.}
% The second suite is the external PolyBench-style kernel suite. 
PolyBench/C is a widely used benchmark family for evaluating compilers and program-transformation systems on structured numeric kernels, especially in work on loop optimisation, polyhedral compilation, and high-performance array code.
% Its programs include small kernels with regular control flow, affine array indexing, and deterministic numeric behaviour, making them convenient for both performance and semantic comparison.
The PolyBench-style suite provides a more objective external check on whether the compiler behaves correctly on recognised array- and loop-dominated workloads that are used outside this project.
The selected kernels are Floyd--Warshall, Jacobi-1D, Jacobi-2D, Seidel-2D, MVT, ATAX, and GESUMMV. Their fixed \texttt{MEDIUM}-class parameters and features exercised are listed in Appendix~\ref{app:evaluation-supplementary}; they are appropriate for Veritas because they are dominated by fixed-size arrays, structured imperative loops, arithmetic side conditions, and deterministic computation over statically bounded data.

\paragraph{Negative suite.}
The \texttt{negative\_suite} contains 35 intentionally invalid Veritas programs. It is used to evaluate source-level rejection across representative failure classes, including type errors, undefined names, invalid calls, array bounds violations, unsatisfied preconditions, invalid quantifier use, invariant failures, division-by-zero risks, and integer overflow or underflow hazards.

\paragraph{Verification-stress suite.}
The \texttt{verification\_stress\_suite} is a smaller proof-heavy subset of the feature suite. Its purpose is not broad feature coverage, but cost analysis: it collects programs with array initialisation, array assignment, quantifiers, binary search, bubble sort, and sortedness reasoning where source and DTAL proof obligations are expected to be more expensive.

\paragraph{Comparison suite.}
The \texttt{comparison\_suite} contains six normalised verification tasks implemented in Veritas, Dafny, Liquid Haskell, and Verus: safe division, bounded array access with an offset, array initialisation with a loop invariant, binary search, sorted-head extraction, and overflow-safe midpoint arithmetic. The suite is normalised by verified property rather than by identical data representation, since each language expresses arrays and specifications differently.

\paragraph{DTAL tampering corpus.}
The DTAL tampering corpus starts from valid compiled DTAL, applies small syntax-preserving mutations, and checks that standalone DTAL verification rejects the result. It is used to test the untrusted-compiler trust boundary directly, with mutations covering structural mismatches, strengthened preconditions, contradictory assertions, bounds failures, arithmetic overflow, ownership violations, mutable aliasing, and entry-state mismatches.

\section{Qualitative analysis}\label{sec:qualitative-analysis}

\subsection{DTAL design and implementation}\label{sec:dtal-eval}

% In the Veritas architecture, DTAL must be expressive enough to carry the facts needed for independent low-level checking. The evaluation therefore considers whether the implemented DTAL supports the intended trust architecture, rather than whether it is a complete reimplementation of Xi and Harper's formal system.

\subsubsection{Relationship to Xi and Harper's DTAL}

Veritas is inspired directly by Xi and Harper's DTAL and preserves the mechanisms most relevant to independent low-level verification:
\begin{itemize}
  \item \textbf{Dependent block or label state.} This supports control-flow safety by ensuring that jumps and joins are only valid when the incoming machine state matches the target's expected typing context.
  \item \textbf{Singleton integer typing.} This supports arithmetic and indexing safety, since later instructions can rely on those symbolic facts when proving side conditions.
  \item \textbf{Size-indexed arrays.} This supports array-bounds safety by making out-of-bounds reads and writes statically checkable.
  \item \textbf{Typed stack discipline.} This supports structural safety by preventing ill-typed stack use across calls, returns, and local temporaries.
  \item \textbf{Proof-relevant typed memory access.} This supports static memory-safety guarantees such as array-bound-check elimination.
\end{itemize}

Veritas narrows the original design in several directions. Xi and Harper's DTAL includes general tuple and array allocation primitives, existential dependent types in a broader form, and an extension for sum and tag reasoning. Veritas instead focuses on the low-level facts needed for fixed-size arrays, arithmetic side conditions, contracts, and borrow-aware compilation. This sacrifices some theoretical generality in exchange for automation and a logical fragment that fits SMT-backed checking.

The important continuity is the independent low-level verification model. The Veritas version of the copy-loop style example from Section~\ref{sec:dtal-background} uses different syntax, but still records block assumptions, symbolic arithmetic, and a typed memory access in the low-level artifact itself:

\begin{quote}
  \begin{verbatim}
.entry {v0: int}
.assume (v0 >= 0 && v0 < 4)
add v9, v0, v8    : {_synth_0: int | _synth_0 == (i + 1) }
.assert true
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}

The verifier can therefore justify the array access from the DTAL type and constraint context rather than relying on a dynamic bounds check or on the compiler's internal reasoning.

\subsubsection{Extensions and deviations}

Veritas also extends DTAL in directions not targeted by Xi and Harper. First, source-level obligations survive lowering as explicit low-level refinements:
\begin{quote}
  \begin{verbatim}
div v2, v0, v1    : {_synth_0: int | _synth_0 == (a / b) }
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}
These obligations are not trusted as compiler-issued certificates; they are re-checked by the verifier against the emitted low-level code. This provides broader source-to-low-level continuity for the fragment Veritas supports, including bounds facts, contract-style obligations, and borrow-related safety constraints. Carrying more annotations gives an untrusted compiler more ways to emit inconsistent DTAL, but this increases the risk of false rejection rather than false acceptance.

Second, Veritas adds explicit ownership and borrow-aware operations. This pushes alias-control properties below the frontend, so that creation, use, and termination of borrows are represented and re-checked in DTAL:

\begin{quote}
  \begin{verbatim}
alias_borrow v3, v1    : &[int(7); 1]
load v5, [v3 + v4]     : int
borrow_end v3          : &[int(7); 1]
\end{verbatim}
\end{quote}

Here, \texttt{alias\_borrow} creates the shared borrowed view \texttt{v3}, the \texttt{load} uses that view, and \texttt{borrow\_end} terminates it. The verifier checks that the access occurs through a live borrow and that the borrow is ended consistently with the source-language ownership discipline.

Finally, Veritas introduces a physical DTAL stage after register allocation. Xi and Harper's DTAL is closest to Veritas' virtual DTAL: an abstract typed assembly before register allocation and spill. Physical DTAL instead exposes scratch-register use, spills, prologues/epilogues, and instruction expansions:

\begin{quote}
  \begin{verbatim}
mov lr, r1    : int
cqo
idiv r7
mov r0, lr    : int
\end{verbatim}
\end{quote}

or in explicit stack and calling-convention machinery such as
\texttt{spill\_store}, \texttt{spill\_load}, \texttt{.prologue}, and
\texttt{.epilogue}.
This makes DTAL less elegant than the idealised presentation, but it moves more backend work outside the trusted path. Register allocation and instruction expansion become part of the untrusted compiler because their results are still checked before final encoding.

\subsection{Veritas as a systems-language toolchain}\label{sec:veritas-sys-eval}

% This subsection evaluates whether Veritas has enough systems-language structure to make the later compiler and runtime measurements meaningful. The comparison is deliberately scoped: Veritas is not a mature C/Rust competitor, but it should support enough low-level imperative programming to justify evaluation as a small verified systems-language toolchain.

\subsubsection{Systems-language feature comparison}

Compared with C and Rust, Veritas currently occupies an intermediate position. Like both languages, it supports first-order functions, mutable local state, fixed-size arrays, explicit integer reasoning, loop-based imperative control flow, and compilation to native code. Like Rust, it also has an ownership- and borrow-aware safety story rather than relying purely on unrestricted memory
manipulation. Unlike both, however, its design is centred around carrying verification-relevant information through the compilation pipeline. This makes Veritas less general-purpose than C or Rust as a production systems language, but also gives it a stronger explicit safety and trust architecture within its supported fragment.

\section{Quantitative analysis}\label{sec:quantitative-analysis}

\subsection{Compiler functional correctness}

Compiler correctness is evaluated empirically rather than by proof. The 28-program feature suite checks that representative Veritas programs compile and execute successfully, while the seven PolyBench kernels check semantic agreement against C baselines using deterministic checksums. All feature-suite programs and all PolyBench kernels passed their semantic checks. This supports a suite-bounded correctness claim for the implemented compiler, but not a CompCert-style semantic preservation theorem.

\subsection{Verifier functional correctness and reliability}\label{sec:verifier-correctness}

% This section evaluates the verifier itself as an independent checking mechanism. The claim is practical reliability, not a formal proof of verifier correctness.

The frontend compiler and the independent physical-DTAL verifier agree on acceptance for all 28 feature-suite programs. This covers arrays, preconditions, loop invariants, quantifiers, sortedness, shared and mutable borrows, scalar dereferences, and overflow-aware arithmetic.

The negative suite provides complementary source-level rejection evidence: all 35 intentionally invalid programs are rejected. The DTAL tampering corpus then tests the trust boundary directly by mutating valid low-level artifacts after compilation. All 14 tampered low-level programs are rejected. For example, changing \texttt{.returns int} to \texttt{.returns bool} is rejected as a structural mismatch, while changing an in-bounds singleton index to an out-of-bounds one is rejected as a bounds failure.

The verifier-side Rust core is \num{7817} lines out of \num{42996}, or 18.2\% of the counted Rust implementation. This leaves most compiler infrastructure outside the trusted path for the checked safety policy. The remaining trusted components are the verifier, solver, encoder, and small runtime/bootstrap artifacts.

\section{Summary against project aims}

The evaluation supports the three aims set out for Veritas: a DTAL-based trust architecture, a verification-oriented source language with useful expressivity, and a practical enough systems-language toolchain for the supported fragment. The strongest result is architectural: safety-relevant information survives lowering into an independently checkable artifact, and the empirical evidence shows that this artifact can reject both source-level mistakes and representative backend corruptions. The TCB analysis reinforces the same point by showing that most compiler infrastructure is outside the trusted path for the checked safety policy.

The expressivity results are deliberately scoped. Veritas does not match mature verification ecosystems on heap-shaped data, recursive proofs, concurrency, or protocol-heavy reasoning, but it does cover the contract, array, arithmetic, invariant, quantified, sortedness, and borrowing properties needed to exercise the trust architecture. This is enough to demonstrate the central source-to-DTAL evidence-carrying design without overstating the language as a general-purpose verifier.

The practicality results are positive but qualified in the same way. Veritas produces executable native artifacts and runs non-trivial external kernels, but the evidence is strongest for fixed-size arrays, structured loops, local mutation, contracts, invariants, and borrow-oriented examples. The feature suite is curated rather than exhaustive, the PolyBench results demonstrate behaviour on structured numeric kernels rather than arbitrary systems programs, and the tampering corpus covers representative backend corruptions rather than all possible miscompilations.

Overall, the chapter shows that Veritas satisfies the dissertation aims as a scoped verified systems-language prototype: the architecture works, the source language is expressive enough for the intended verification tasks, and the implementation is practical enough to evaluate on real compiled programs. The claims remain deliberately bounded: cross-system comparisons are informative but not perfectly like-for-like, the verifier evidence is empirical rather than a formal soundness proof.
