\chapter{Evaluation}\label{ch:eval}

\section{Evaluation goals and methodology}

The purpose of this chapter is to evaluate Veritas as both a verified
programming language implementation and a research prototype for
type-preserving compilation. The dissertation's central claim is not merely
that a small source language can be checked with refinement types, but that
proof-relevant information can be preserved to a low-level representation and
independently re-checked there. The evaluation therefore has to cover several
distinct questions: whether the DTAL design and implementation are a useful
realisation of the intended trust architecture, whether Veritas is plausible as
a systems-language toolchain, whether the source language is expressive enough
for the targeted verification tasks, what the costs of source-level and
DTAL-level checking are, how reliable the independent verifier is in practice,
and what the resulting trusted computing base looks like.

These questions correspond directly to the project's success criteria. A strong
evaluation for this project cannot stop at frontend acceptance rates or runtime
benchmarks alone. It must distinguish source-language verification from
independent DTAL verification, justify the chosen benchmark suites, and show
both correctness and cost evidence for the supported fragment. It must also be
clear about what is not being claimed: this chapter does not attempt a
foundational proof of compiler correctness, nor does it claim support for all
systems-programming idioms. Instead, it evaluates the implemented fragment
systematically and argues for the usefulness of the resulting architecture.

\subsection{Evaluation questions}

The chapter is organised around six evaluation questions.

First, how faithfully and usefully has DTAL been implemented for this project?
This is partly a design question: Veritas is inspired by Xi and Harper's DTAL,
but it is not a literal reproduction. The evaluation therefore needs to assess
which core ideas were preserved, which were adapted, and whether the resulting
low-level language is sufficient to support independent checking of the
compiler's output.

Second, is Veritas viable as a systems-language toolchain rather than only a
verification toy language? This requires evaluating the source language and
toolchain in terms familiar from systems programming: mutable state, arrays,
integer reasoning, low-level code generation, runtime behaviour, and the
ability to compile non-trivial kernels to executable code.

Third, is the source language expressive enough for the project's intended
verification tasks? This question concerns contracts, loop invariants,
quantifiers, array reasoning, arithmetic safety, and borrow-like alias
discipline. It also motivates comparison with source-level verification systems
such as Dafny, Liquid Haskell, and Verus, which occupy related but different
points in the expressiveness--automation design space.

Fourth, what is the cost of verification? For Veritas, this must be split
carefully into source-to-DTAL compilation cost, frontend SMT cost, explicit
DTAL-level verification cost, and end-to-end wall-clock command latency. This
distinction matters because most comparison systems primarily incur only
source-level verification cost, whereas Veritas can also pay for independent
low-level re-checking.

Fifth, how reliable is the independent verifier itself? This is evaluated not
only by agreement on valid source programs, but also by rejection of invalid
source programs, rejection of intentionally tampered DTAL, and robustness tests
for determinism and implementation stability.

Finally, what does the trusted computing base look like in practice? The trust
architecture is one of the main research contributions of the project, so the
evaluation must quantify which components remain trusted, how large that trusted
set is relative to the whole implementation, and how this differs from more
conventional source-level verification architectures.

\subsection{Experimental artifacts and benchmark suites}

The evaluation uses a fixed set of named suites so that every quantitative
claim can be tied to a stable input population rather than an ad hoc selection
of examples. The \texttt{feature\_suite} is the main positive corpus for
supported-language correctness and expressiveness claims. It contains curated
valid programs spanning conditionals, arrays, mutation, preconditions, loop
invariants, quantifiers, safe arithmetic, sortedness reasoning, and
borrow-related examples. The \texttt{negative\_suite} is the complementary
rejection corpus and contains the full committed set of intentionally invalid
programs. It is used to evaluate systematic rejection of ill-typed or unsafe
programs rather than only a hand-picked subset of failures.

Two additional suites serve more specialised roles. The
\texttt{verification\_stress\_suite} contains proof-heavy programs chosen
specifically for cost analysis, where solver load and verification overhead are
expected to be informative. The \texttt{algorithm\_suite} is used for runtime
and practicality evidence, and is complemented by the external
\texttt{polybench\_suite} of translated PolyBench-style kernels. These runtime
benchmarks are treated as external practicality evidence rather than as the
primary correctness suite.

Two further artifacts support the trust and comparison claims. The
\texttt{dtal\_tampering} corpus starts from valid curated programs, compiles
them to DTAL, applies small syntax-preserving mutations, and checks that
standalone DTAL verification rejects the tampered low-level program. This
directly tests the untrusted-compiler story. The \texttt{comparison\_suite}
contains matched programs written for Veritas, Dafny, Liquid Haskell, and
Verus, and is used to compare verification cost and annotation burden across a
small number of comparable tasks.

All dissertation-facing quantitative results are derived from chapter-labelled
runs collected by the manifest-driven evaluation harness in
\texttt{eval/bench.sh}. These run directories preserve raw outputs, derived
tables, exact commands, suite manifests, machine information, and tool
versions. The chapter therefore cites named artifacts rather than informal
measurements, and the final tables can be traced back to reproducible run
directories.

\subsection{Measurement conventions}

Several measurement conventions are important for interpreting the results
correctly. First, the chapter distinguishes internal phase timings from
external wall-clock timings. Internal metrics are obtained from
\texttt{veritas --bench}: \texttt{compile\_ms} measures source-to-DTAL
compilation, \texttt{verify\_ms} measures the explicit independent DTAL
verification stage, and the frontend and verifier SMT counters record solver
activity in those two stages separately. These are used to explain where cost
comes from. External timings, by contrast, are measured with
\texttt{hyperfine} and represent end-to-end command latency, including process
startup and native-output generation. They are used for user-visible
performance claims. These two timing layers are intentionally kept separate and
must not be conflated.

Second, runtime correctness is evaluated semantically rather than by exit code
alone. For trivial cases, an exit status may itself be the intended result, but
for algorithmic kernels the harness uses exact outputs or deterministic
checksums. This is important because successful process termination is weaker
evidence than functional agreement on the computed result.

Third, the cross-system comparison suite measures both verification time and
annotation burden. For each comparison file, the evaluation records total lines
of source, lines counted as specification or annotation, lines counted as
executable code, and the resulting annotation-to-code ratio. These counts are
heuristic rather than language-theoretically perfect, but the counting rule is
made explicit and applied consistently across the suite. The purpose is to
compare broad verification effort rather than to claim exact syntactic
minimality.

Finally, comparisons with Dafny, Liquid Haskell, and Verus must be interpreted
carefully because Veritas performs two separable kinds of checking: source-level
proof discharge and independent DTAL-level verification. Most related systems
in the comparison operate primarily at the source level. For this reason, the
chapter distinguishes frontend-only cost from end-to-end Veritas verification
cost and treats the additional DTAL-level checking as a feature of the trust
architecture rather than as a directly like-for-like penalty in every table.

\section{DTAL design and implementation}

The DTAL layer is central to the dissertation's trust argument, so it needs to
be evaluated as a contribution in its own right rather than treated only as an
implementation detail of the backend. The relevant question is not whether
Veritas reproduces Xi and Harper's DTAL exactly, but whether it preserves the
key purpose of DTAL: to place a small, independently checkable typed assembly
language between an untrusted compiler and executable machine code. The answer
is broadly positive. Veritas retains the essential architecture of
type-preserving compilation to a low-level representation with explicit type
states and proof-relevant annotations, while adapting the language to the needs
of a practical compiler for arrays, refinement-carrying arithmetic, and a
borrow-aware systems language. At the same time, the implemented DTAL is
best understood as an engineering realisation influenced by Xi and Harper,
rather than as a fully faithful formal port of the 2001 system.

\subsection{Relationship to Xi and Harper's DTAL}

The strongest continuity with Xi and Harper's DTAL lies in the verification
model. As in the original design, low-level code is not trusted merely because
it was emitted by the compiler. Instead, each basic block carries a type state,
instructions are checked by re-deriving their types from their operational
meaning, and control-flow joins are validated by checking compatibility of the
incoming states. This is the crucial property that distinguishes DTAL from
ordinary compiler IR annotation schemes: the low-level artifact is not only
typed, but independently checkable using only the information embedded in the
assembly itself. Veritas follows this design directly, and the independent
verifier is therefore not an auxiliary debugging tool but an intended consumer
of the DTAL output.

At the same time, several aspects of the original DTAL are simplified or
adapted. Veritas works with a much narrower language and proof domain than a
general dependently typed assembly language: the logical fragment is chosen to
match SMT-backed refinement checking, array bounds reasoning, and simple
arithmetic safety properties rather than arbitrary proof terms. Proofs are
represented operationally through constraints, singleton types, block entry
states, assertions, and preconditions/postconditions, rather than through the
full richness of a foundational typed assembly formalism. This is a deliberate
tradeoff. The implemented system sacrifices some theoretical generality in
exchange for automation and a verification model that fits the rest of the
toolchain.

This tradeoff is appropriate for the dissertation's aims. The project is not
trying to replace a foundational proof-carrying assembly framework, nor to
rebuild the full metatheory of the original DTAL. Instead, it uses the DTAL
architecture as a way to move the trust boundary downward, allowing
source-language facts to survive compilation in a form that is still checkable
after register allocation and backend lowering. Evaluated against that goal,
Veritas's DTAL is faithful in the most important sense: it preserves the idea
that low-level safety should be re-established independently of the compiler.

\subsection{Feature parity, extensions, and deviations}

The implemented DTAL also differs from the original design in ways that are
substantively useful for this project. The most important extension is support
for the proof obligations that arise naturally from the Veritas source
language: fixed-size arrays, indexed loads and stores with explicit bounds
proofs, refinement-carrying arithmetic values, function contracts, quantified
constraints, and symbolic facts introduced by control flow. These are not
incidental annotations. They are precisely the information needed for the
standalone verifier to re-check the safety of array accesses, the preservation
of arithmetic facts, and the soundness of contract-guided calls after
compilation.

A second important deviation is the introduction of explicit ownership and
borrow-aware operations. Xi and Harper's DTAL was not designed around a
Rust-like ownership discipline, whereas Veritas carries object ownership,
shared borrows, mutable borrows, and borrow termination through DTAL as
first-class phenomena. This extension is evaluatively significant because it
pushes alias-control properties below the frontend. In other words, the project
does not merely check borrow discipline before lowering and then hope the
backend preserves it; the relevant low-level operations are represented and
re-checked in DTAL. This is one of the clearest places where Veritas diverges
from the original DTAL design in order to serve its systems-language setting.

The physical-DTAL pipeline introduces a further pragmatic deviation. The
default backend does not verify only the virtual-register typed assembly.
Instead, it uses an untrusted physical allocation pass to map virtual DTAL to a
physically allocated DTAL with explicit scratch-register use, spills,
prologues/epilogues, and instruction expansions such as division. The verifier
then checks this physical DTAL before direct encoding. This is not present in
Xi and Harper's original presentation, but it is one of the most important
engineering decisions in Veritas because it shrinks the trusted backend and
makes register allocation and instruction expansion part of the untrusted
compiler. The resulting DTAL is therefore less abstract than the original
idealised typed assembly, but more useful for the project's trust model.

There are, however, deliberate restrictions. The current DTAL fragment is
geared toward sequential control flow, fixed-size arrays, lexical borrow
discipline, and a hosted or bare-metal runtime model with a small set of
intrinsics. It does not aim to model arbitrary heap structures, unrestricted
pointers, concurrency, or the full range of low-level effects found in general
systems code. These are not accidental omissions; they are part of the chosen
scope that keeps the low-level verification story coherent and mechanically
checkable.

\subsection{Evaluation of the DTAL design}

From an evaluation perspective, the most important result is that the DTAL
design enables forms of checking that a source-only verifier cannot provide on
its own. Because contracts, bounds facts, ownership-transfer operations, and
block-entry states are preserved into DTAL, the verifier can reject not only
ill-typed source programs but also malformed low-level programs produced by an
incorrect backend. The dedicated DTAL-tampering corpus demonstrates this
directly: when valid compiled programs are modified so that they violate return
contracts, bounds obligations, ownership rules, arithmetic safety conditions,
or structural typing constraints, standalone DTAL verification rejects them.
This is exactly the kind of evidence that the DTAL layer is supposed to make
possible.

The design is also expressive enough for the intended low-level checks within
the supported fragment. The feature suite and verifier-agreement results show
that the DTAL representation can carry enough information for independent
re-checking of non-trivial source programs involving arrays, quantified facts,
loop invariants, sortedness properties, safe division, overflow-aware
arithmetic, and borrow-oriented examples. In this sense, the implemented DTAL
is not merely a logging format for the frontend's proof results; it is a usable
verification target with enough structure to support the chapter's trust and
correctness claims.

The main tradeoff is complexity at the low level. Physical DTAL necessarily
exposes register assignments, spill slots, calling-convention details, and
instruction expansion that are absent from the source language. This makes the
representation less elegant than an idealised typed assembly and increases the
burden on the verifier. However, this tradeoff is justified by the trust-model
benefit: the more of the backend that is represented in DTAL, the less of the
backend has to remain trusted. The implementation therefore prefers a somewhat
heavier low-level artifact in exchange for a smaller and more auditable trusted
path.

Overall, the DTAL design should be judged a success relative to the dissertation's
goals. It does not provide the full generality of a foundational typed assembly
framework, but it does achieve the essential architectural purpose of DTAL in a
practical compiler setting: the compiler remains untrusted, proof-relevant
information is preserved below the frontend, and the final low-level program is
substantial enough to be independently re-checked before code generation
completes.
