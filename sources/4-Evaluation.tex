\subsection{Experimental artifacts}

\paragraph{feature-suite.}

I wrote a suite of 28 programs covering all main program features. Its purpose is to evaluate the compiler and verifier's performance and functional correctness on representative source-language features and proof obligations.

\paragraph{PolyBench.}
PolyBench/C~\cite{PouchetPolyBenchC32} is a widely used benchmark family for evaluating compilers and program-transformation systems on structured numeric kernels, especially in work on loop optimisation, polyhedral compilation, and high-performance array code.
The PolyBench suite provides an external check on whether the compiler behaves correctly on recognised array- and loop-dominated workloads.
The selected kernels are Floyd--Warshall, Jacobi-1D, Jacobi-2D, Seidel-2D, MVT, ATAX, and GESUMMV. Their fixed \texttt{MEDIUM}-class parameters and features exercised are listed in Appendix~\ref{app:evaluation-supplementary}; they are appropriate for Veritas because they are dominated by fixed-size arrays, structured imperative loops, arithmetic side conditions, and deterministic computation over statically bounded data.

\paragraph{Negative suite.}
I wrote a suite of 35 intentionally invalid Veritas programs. It is used to evaluate source-level rejection across representative failure classes, including type errors, undefined names, invalid calls, array bounds violations, unsatisfied preconditions, invalid quantifier use, invariant failures, division-by-zero risks, and integer overflow or underflow hazards.

\paragraph{Comparison suite.}
The \texttt{comparison\_suite} contains six normalised verification tasks implemented in Veritas, Dafny, Liquid Haskell, and Verus: safe division, bounded array access with an offset, array initialisation with a loop invariant, binary search, sorted-head extraction, and overflow-safe midpoint arithmetic. The suite is normalised by verified property.
% rather than by identical data representation, since each language expresses arrays and specifications differently.

\paragraph{DTAL tampering corpus.}
The DTAL tampering corpus starts from valid compiled DTAL, applies small syntax-preserving mutations, and checks that standalone DTAL verification rejects the result. It is used to test the untrusted-compiler trust boundary, with mutations covering structural mismatches, strengthened preconditions, contradictory assertions, bounds failures, arithmetic overflow, ownership violations, mutable aliasing, and entry-state mismatches. % TODO: put list in appendix

\subsection{Measurement methodology}

All dissertation-facing quantitative results are derived from fixed suite manifests. The measurements distinguish internal phase timings, such as compilation, verification, and SMT time, from external wall-clock command latency. Repeated wall-clock measurements use \texttt{hyperfine} with 30 measured runs and 5 warmup runs, reporting the mean and standard deviation. For reproducibility, the evaluation preserves raw timing output, exact commands, run metadata, suite manifests, tool-version information, and git status in the run directory. These conventions keep user-visible latency claims separate from internal cost attribution. % TODO: machine specs?

\section{Qualitative analysis}\label{sec:qualitative-analysis}

\subsection{DTAL design and implementation}\label{sec:dtal-eval}

% In the Veritas architecture, DTAL must be expressive enough to carry the facts needed for independent low-level checking. The evaluation therefore considers whether the implemented DTAL supports the intended trust architecture, rather than whether it is a complete reimplementation of Xi and Harper's formal system.

\subsubsection{Core DTAL features for low-level verification}

For Veritas to support the intended trust architecture, its DTAL must be expressive enough to carry the facts needed by the standalone verifier. Instead, the question is whether the implemented DTAL enables verification of the project's scoped safety policy at the low level via the chosen mechanisms:
\begin{itemize}
  \item \textbf{Dependent block or label state} support control-flow safety by ensuring that jumps and joins are only valid when the incoming machine state matches the target's expected typing context.
  \item \textbf{Singleton integer typing} supports arithmetic and indexing safety, since later instructions can rely on those symbolic facts when proving side conditions.
  \item \textbf{Size-indexed arrays} support array-bounds safety by making out-of-bounds reads and writes statically checkable.
  \item \textbf{Typed stack discipline} supports structural safety by preventing ill-typed stack use across calls, returns, and local temporaries.
  \item \textbf{Proof-relevant typed memory access} supports static memory-safety guarantees such as array-bound-check elimination.
\end{itemize}

This feature set is deliberately narrower than Xi and Harper's full DTAL. Veritas focuses on the low-level facts needed for fixed-size arrays, arithmetic side conditions, contracts, and borrow-aware compilation. The narrower design sacrifices some theoretical generality in exchange for automation and a logical fragment that fits SMT-backed checking.

The important continuity with Xi and Harper's design is the independent low-level verification model. The Veritas version of the copy-loop style example from Section~\ref{sec:dtal-background} uses different syntax, but still records block assumptions, symbolic arithmetic, and a typed memory access in the low-level artifact itself:

\begin{quote}
  \begin{verbatim}
.entry {v0: int}
.assume (v0 >= 0 && v0 < 4)
add v9, v0, v8    : {_synth_0: int | _synth_0 == (i + 1) }
.assert true
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}

The verifier can therefore justify the array access from the DTAL type and constraint context rather than relying on a dynamic bounds check or on the compiler's internal reasoning.

\subsubsection{Extensions and deviations}

Veritas also extends DTAL in directions not targeted by Xi and Harper. First, source-level obligations survive lowering as explicit low-level refinements:
\begin{quote}
  \begin{verbatim}
div v2, v0, v1    : {_synth_0: int | _synth_0 == (a / b) }
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}
These obligations are re-checked by the verifier against the emitted low-level code. Re-checking the obligations provides broader source-to-low-level continuity for the fragment Veritas supports, including bounds facts, contract-style obligations, and borrow-related safety constraints. Carrying more annotations gives an untrusted compiler more ways to emit inconsistent DTAL, but the main consequence is false rejection rather than false acceptance.

Second, Veritas adds explicit ownership and borrow-aware operations. These operations push alias-control properties below the frontend, so that creation, use, and termination of borrows are represented and re-checked in DTAL:

\begin{quote}
  \begin{verbatim}
alias_borrow v3, v1    : &[int(7); 1]
load v5, [v3 + v4]     : int
borrow_end v3          : &[int(7); 1]
\end{verbatim}
\end{quote}

Here, \texttt{alias\_borrow} creates the shared borrowed view \texttt{v3}, the \texttt{load} uses that view, and \texttt{borrow\_end} terminates it. The verifier checks that the access occurs through a live borrow and that the borrow is ended consistently with the source-language ownership discipline.

Finally, Veritas introduces a physical DTAL stage after register allocation. Physical DTAL exposes scratch-register use, stack spills, prologues and epilogues, calling-convention details, and instruction expansions such as machine-level division. These details are represented explicitly rather than hidden behind an idealised virtual assembly model. Physical DTAL is less elegant than the idealised presentation, but it moves more backend work outside the trusted path.

\section{Quantitative analysis}\label{sec:quantitative-analysis}

\subsection{Compiler functional correctness}\label{sec:compiler-correctness-eval}

Compiler correctness is evaluated empirically rather than by proof. The feature-suite checks that representative Veritas programs compile and execute successfully, while the PolyBench kernels check semantic agreement against C baselines using deterministic checksums. All feature-suite programs and all PolyBench kernels passed their semantic checks. The result supports a suite-bounded correctness claim for the implemented compiler.

\subsection{Compiler and runtime practicality}\label{sec:compiler-runtime-practicality}

% Practicality is evaluated through compilation cost, runtime behaviour, and emitted artifact size.

\subsubsection{Compiler throughput}

The curated feature-suite gives a local view of compiler throughput on representative source-language features.
Figure~\ref{fig:feature-suite-compile-cost} shows two related but distinct cost patterns. The binary-search program is one of the most expensive feature-suite examples overall, but its cost is not dominated by frontend SMT time; much of the cost comes from the size and structure of the generated control-flow and verification artifact. By contrast, the array-proof and quantifier-heavy programs spend a larger fraction of their compile time in the SMT-facing frontend. Simpler arithmetic- and borrow-oriented cases remain much cheaper. The pattern therefore suggests that proof-rich programs can become expensive through both solver work and non-solver compiler work, rather than through a single uniform bottleneck.

The PolyBench kernels give a second view on larger loop- and array-heavy programs. Figure~\ref{fig:polybench-compile-cost} shows that several kernels are dominated by frontend SMT work, with \texttt{mvt}, \texttt{atax}, \texttt{jacobi\_1d}, and \texttt{gesummv} spending almost all measured compile time in the SMT-facing frontend. The common feature of these cases is the proof shape generated by the frontend: they combine multiple indexed arrays, repeated loop phases, shifted or transposed accesses, and arithmetic side conditions. These features generate many array-bound and arithmetic proof obligations. Other kernels, including \texttt{floyd\_warshall}, \texttt{jacobi\_2d}, and \texttt{seidel\_2d}, have a much larger non-SMT component because their obligations are mostly direct affine loop-bound checks. The PolyBench timing profile therefore suggests that compile-time practicality is often driven by solver-heavy proof structure, but that raw generated-code and verification-artifact size also matter, given the generated control-flow, arithmetic expressions, and verification artifacts still have to be lowered.

\subsubsection{Cross-system verification-cost comparison}

Figure~\ref{fig:comparison-suite-wallclock} reports wall-clock verification-command latency on the six-task normalised comparison suite.
The comparison assesses whether Veritas has plausible verification latency on a small suite chosen around the properties central to this dissertation. The wall-clock gap is largely explained by what each command invokes. Veritas is a small release binary checking a narrow first-order fragment and, in the compile-plus-verify mode, running its standalone physical-DTAL verifier. Dafny, Liquid Haskell, and Verus invoke larger verification toolchains, including richer frontends, module and library infrastructure, verification-condition generation, and solver orchestration. For such small tasks, this fixed command and toolchain overhead is a substantial part of the measured time. The important methodological distinction is that Veritas reports both frontend-only and compile-plus-DTAL-verification costs for its scoped prototype, whereas the other systems primarily report source-level verification-command cost for mature, more general tools.

The reason is that the suite matches Veritas' built-in proof idioms: fixed-size array types carry length information, bounded \texttt{for} loops introduce range facts automatically, and local arithmetic assumptions can often be written as compact refinement types. The other systems frequently need additional specification scaffolding to express equivalent heap, sequence, sortedness, or termination facts in their more general settings. The comparison is evidence that Veritas is annotation-light on its target fragment, but not necessarily across all verification tasks. The frontend-only view is the fairest comparison point against source-level verification systems. The compile-plus-verify view is the relevant measure for Veritas's trust architecture because it includes the extra low-level checking stage that the other systems do not attempt.

The frontend compiler and the independent physical-DTAL verifier agree on acceptance for all feature-suite programs. The negative suite provides complementary source-level rejection evidence: all invalid programs are rejected. All low-level programs from the DTAL tampering corpus are rejected. A separate semantic-corruption test changes verifier-compatible values while preserving the checked safety policy; the verifier accepts the changed program, as expected, demonstrating that DTAL verification is not a full semantic-equivalence check.
