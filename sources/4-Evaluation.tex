\chapter{Evaluation}\label{ch:eval}

This chapter evaluates Veritas against its goals and success criteria. It begins by assessing the design and implementation of Veritas' DTAL in relation to Xi and Harper's DTAL (Section~\ref{sec:dtal-eval}). It then assesses the Veritas source language and compiler as a systems-language toolchain (Section~\ref{sec:source-lang-eval}), followed by an evaluation of the source language along a separate axis of expressiveness as a verification-oriented system (Section~\ref{sec:source-lang-eval}). Section~\ref{sec:verification-perf} and Section~\ref{sec:verifier-correctness} evaluates the verifier: the cost and performance of performing verification and the functional correctness of its implementation. Finally, Section~\ref{sec:tcb-eval} evaluates the overall trust architecture and size of the TCB.

\section{Evaluation goals and methodology}
% no formalisation/proof of DTAL; does it successfully build on the foundation of xi and harper's DTAL (can their proofs be used as evidence/support here)?

The core goals of Veritas as put forward in the proposal (Appendix [TODO]) and refined in the requirements analysis (Section~\ref{sec:requirements-anal}) were to implement a small systems language, a type-preserving toolchain to compile this language, the DTAL variant that is the target of this compilation pipeline, and a verifier that can independently check DTAL programs for their compliance with defined safety properties. The core memory-safety, control-flow safety and arithmetic safety properties Veritas aimed to support were array bounds checking, state consistency at joins and branches, function contract checking, and integer overflow. These features were fully realised in the implementation presented in Chapter~\ref{ch:impl} in addition to extensions that build on the core goals.

A central claim of Veritas' architecture is that low-level artifacts can be independently verified while the compiler can be untrusted. This was achieved owing to the refinement type system, verification-oriented language features (e.g., function contracts), type-preserving compilation, as well as other components of the languages and compiler. Veritas also aimed to support a toolchain for a \emph{systems language}. This evaluation must therefore address several distinct questions:
\begin{itemize}
  \item Is the design and implementation of DTAL a useful realisation of the intended trust architecture?
  \item Are the source language and compiler implementations viable for a systems-language toolchain?
  \item Is the source language expressive enough for the targeted verification tasks?
  \item Is the additional cost imposed by independent DTAL-level verification practical enough to keep the toolchain usable?
  \item How confident can one be about the correctness of the verifier?
  \item What reduction in the TCB does Veritas achieve, and is that reduction substantial enough to justify the DTAL-based trust architecture?
\end{itemize}

\noindent This chapter explores these questions through relevant experiments and analysis, as well as quantitative and qualitative comparisons with external languages and systems.

\section{DTAL design and implementation}\label{sec:dtal-eval}

In the Veritas architecture, the target DTAL must be expressive enough to enable verification of the required safety properties. Xi and Harper's DTAL design provided a suitable foundation to draw inspiration from; the Veritas DTAL implementation includes a subset of its features for a narrower language but also extends the design in different directions, exploring ownership-aware memory operations, SMT-oriented refinement constraints, and verification of physically allocated code. The evaluation considers to what extent the DTAL implementation supports the intended trust architecture, rather than assessing it as fully faithful formal engineering realisation of Xi and Harper's design.

\subsection{Relationship to Xi and Harper's DTAL}

Veritas is inspired directly by Xi and Harper's DTAL and preserves many of its central features and ideas most relevant for independent low-level verification. Shared features include:
% The shared structure is most clearly seen as a set of concrete mechanisms, each of which supports a corresponding safety property:
\begin{itemize}
  \item \textbf{Dependent block or label state.} Logical state attached to control-flow entry points record assumptions about registers, stack contents, and index variables at the start of a block. This supports control-flow safety by ensuring that jumps and joins are only valid when the incoming machine state matches the target's expected typing context.
  \item \textbf{Singleton integer typing.} Registers can carry exact symbolic integer facts rather than only broad machine types. This supports arithmetic and indexing safety, since later instructions can rely on those symbolic facts when proving side conditions.
  \item \textbf{Size-indexed arrays.} Both systems track array sizes at the type level, so that an array value carries its logical extent alongside its element type. This supports memory safety by making out-of-bounds reads and writes statically checkable.
  \item \textbf{Typed stack discipline.} Both DTALs model stack state rather than treating stack manipulation as untyped raw memory. This supports structural safety by preventing ill-typed stack use across calls, returns, and local temporaries.
  \item \textbf{Proof-relevant typed memory access.} In both systems \texttt{load} and \texttt{store} are checked against the surrounding type and constraint context rather than treated as unchecked primitive operations. This supports static memory-safety guarantees such as array-bound-check elimination.
\end{itemize}

It should be noted that Veritas narrows Xi and Harper's design in some directions. Xi and Harper's DTAL includes general tuple and array allocation primitives, existential dependent types in a broader form, and an extension for sum and tag reasoning. Veritas does not currently expose all of these as first-class DTAL features. Instead, it is more tightly focused on the subset of low-level facts needed for fixed-size arrays, arithmetic side conditions, contracts, and
borrow-aware source-language compilation. The logical fragment is chosen to match SMT-backed refinement checking, array bounds reasoning, and simple arithmetic safety properties rather than arbitrary proof terms.
% Safety evidence is represented operationally
%through constraints, singleton types, block entry states, assertions, and preconditions/postconditions, 
% rather than through the full richness of a foundational typed assembly formalism. 
This is a tradeoff where the implemented system sacrifices some theoretical generality in exchange for automation and a verification model that fits the rest of the toolchain. Given that the project's goal was not to recreate the full metatheory of Xi and Harper's DTAL, this is an appropriate restriction.
% Instead, the aim was to show the DTAL architecture could be used to move the trust boundary downwards and allow source-language facts to survive compilation in a form that is still checkable.

The most important continuity with Xi and Harper's DTAL lies in the independent low-level verification model, which is enabled through the design of Veritas' DTAL. To demonstrate, below shows the Veritas version of the copy loop from Section~\ref{sec:dtal-background},
% This continuity can be seen directly in the instruction style. Xi and Harper's DTAL presents a copy loop using typed labels and register-indexed array access:
%
% \begin{quote}
%   \begin{verbatim}
% loop: {m:nat, n:nat | m <= n, i:nat}
% [r1: int array(m), r2: int array(n), r3: int(m), r4: int(i)]
% sub r5, r4, r3
% bgte r5, finish
% load r5, r1(r4)
% store r2(r4), r5
% \end{verbatim}
% \end{quote}
which preserves the same basic idea of typed labels and register-indexed array access, although the surface syntax is adapted to its implementation:

\begin{quote}
  \begin{verbatim}
.entry {v0: int}
.assume (v0 >= 0 && v0 < 4)
add v9, v0, v8    : {_synth_0: int | _synth_0 == (i + 1) }
.assert true
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}

The low-level program records sufficient information for the verifier to justify array access from the surrounding type and constraint context rather than relying on a dynamic bounds check.

\subsection{Extensions and deviations}

% Veritas also extends the design along axes that Xi and Harper's DTAL did not target.
% Notably, it adds ownership and borrowing operations,distinguishing shared borrows, mutable borrows, ownership transfer, and borrow termination. It also introduces a physical-DTAL layer, so that the verifier can operate after register allocation and instruction expansion rather than only on an idealised virtual assembly. 

Veritas preserves the same basic typed memory access idea, but also extends it with explicit refinement-carrying annotations that originate in source-level proof obligations, for example:
\begin{quote}
  \begin{verbatim}
div v2, v0, v1    : {_synth_0: int | _synth_0 == (a / b) }
load v10, [v1 + v9]    : int(7)
  \end{verbatim}
\end{quote}
This illustrates that memory accesses are still justified by visible low-level constraints, but an arithmetic fact derived at the source-level has been preserved through lowering in symbolic SMT-friendly form. These carried obligations are re-checked by the verifier against the low-level code. This provides a broader source-to-low-level continuity for the particular fragment Veritas supports, including not just bounds facts but also contract-style and borrow-related safety obligations. Preserving additional proof-relevant annotations does increase the surface on which an untrusted compiler can introduce inconsistencies, and therefore may increase the risk of false rejection. However the added annotations also make backend mistakes visible to the independent verifier, and this only expands the rejection surface rather than the acceptance surface.

Another notable extension is the introduction of explicit ownership and borrow-aware operations. Xi and Harper's DTAL was not designed around a Rust-like ownership discipline, whereas Veritas carries object ownership, shared borrows, mutable borrows, and borrow termination through DTAL as first-class phenomena. This extension pushes alias-control properties below the frontend where the relevant low-level operations are represented and re-checked in DTAL. This is a significant divergence from Xi and Harper's DTAL in order to serve a systems-language setting.

\begin{quote}
  \begin{verbatim}
alias_borrow v3, v1    : &[int(7); 1]
load v5, [v3 + v4]     : int
borrow_end v3          : &[int(7); 1]
  \end{verbatim}
\end{quote}

In this example, the creation, use, and termination of the borrowed view is represented explicitly in DTAL, which allows the verifier that the access occurs through a live borrow and that the borrow is ended consistently with the source-language ownership discipline.

% There is no analogue to this ownership-aware low-level operation set in the original DTAL presentation. Instructions such as \texttt{move\_owned}, \texttt{alias\_borrow}, \texttt{borrow\_mut}, and \texttt{borrow\_end} are therefore genuine extensions rather than mere syntactic reformulations.

Due to the architectural decision to perform verification after physical register allocation, Veritas defines a `physical DTAL' (the post-regalloc form of `virtual DTAL') with explicit scratch-register use, spills, prologues/epilogues, and instruction expansions. Xi and Harper's DTAL is most akin to Veritas' virtual DTAL as its semantics are given over an abstract machine, and register allocation and spill is explicitly not modelled in the language.
% The resulting DTAL is therefore less abstract than the original idealised typed assembly, but more useful for the project's trust model.
% However, this tradeoff is justified by the trust-model benefit: the more of the backend that is represented in DTAL, the less of the backend has to remain trusted. The implementation therefore prefers a somewhat heavier low-level artifact in exchange for a smaller and more auditable trusted path.

% The physical-DTAL pipeline introduces a further pragmatic deviation. The backend uses an untrusted physical allocation pass to map virtual DTAL to a physically allocated DTAL with explicit scratch-register use, spills, prologues/epilogues, and instruction expansions such as division. The verifier then checks this physical DTAL before direct encoding. This is not present in Xi and Harper's original presentation, but it is one of the most important engineering decisions in Veritas because it shrinks the trusted backend and makes register allocation and instruction expansion part of the untrusted compiler. The resulting DTAL is therefore less abstract than the original idealised typed assembly, but more useful for the project's trust model.

The difference is visible in instructions such as:

\begin{quote}
  \begin{verbatim}
mov lr, r1    : int
cqo
idiv r7
mov r0, lr    : int
\end{verbatim}
\end{quote}

or in explicit stack and calling-convention machinery such as
\texttt{spill\_store}, \texttt{spill\_load}, \texttt{.prologue}, and
\texttt{.epilogue}.
% These do not make the language closer to the original paper's abstract presentation, but they do make it a stronger intermediate artifact for verifying the real backend pipeline that Veritas actually uses.
The main tradeoff of Veritas' architecture to support physical DTAL is complexity at the low level. Physical DTAL necessarily exposes register assignments, spill slots, calling-convention details, and instruction expansion that are absent from the source language. This makes the representation less elegant than an idealised typed assembly and increases the burden on the verifier. However, this design makes register allocation and instruction expansion part of the untrusted compiler, which is more useful for the project's trust model.

\section{Veritas as a systems-language toolchain}\label{sec:veritas-sys-eval}

The previous section evaluated DTAL as a mechanism that supports the trust architecture. This section evaluates Veritas from the angle of a systems-language toolchain

The previous section evaluated DTAL as a mechanism that supports the trust architecture. This section evaluates Veritas from the angle of a systems-language toolchain that happens to incorporate verification, rather than as a verification system that happens to emit code. This distinction matters because the project claims more than source-level proof automation. It claims to provide a small systems-oriented language that can compile to
executable programs, support structured numeric kernels, and preserve safety
relevant information through the backend. The evaluation therefore considers
language-level systems features, compiler functional correctness, and the
practical behaviour of the generated code.

\subsection{Systems-language feature comparison}

Compared with C and Rust, Veritas currently occupies an intermediate position.
Like both languages, it supports first-order functions, mutable local state,
fixed-size arrays, explicit integer reasoning, loop-based imperative control
flow, and compilation to native code. Like Rust, it also has an ownership- and
borrow-aware safety story rather than relying purely on unrestricted memory
manipulation. Unlike both, however, its design is centred around carrying
verification-relevant information through the compilation pipeline. This makes
Veritas less general-purpose than C or Rust as a production systems language,
but also gives it a stronger explicit safety and trust architecture within its
supported fragment.

The most important implication of this comparison is that Veritas should not be
judged as a drop-in replacement for C or Rust. The current language fragment is
deliberately narrower. It handles mutation, arrays, integer safety, and
borrow-style alias control well enough to support a class of systems-oriented
programs and numeric kernels, but it does not yet provide a complete story for
general pointers, arbitrary heap structure manipulation, or concurrency. The
evaluation should therefore treat ``systems-language viability'' as a claim
about the supported fragment and generated toolchain behaviour, not about full
feature parity with mature production languages.

\subsection{Compiler functional correctness}

The compiler's functional-correctness evaluation is intentionally empirical and
corpus-based rather than foundational. The relevant question is whether the
implemented compiler produces executable programs whose behaviour agrees with
the intended semantics on the evaluated suite, not whether the compiler has
been proved semantically correct for all programs. Two kinds of evidence are
used here. Table~\ref{tab:compiler-correctness-summary} summarises the current
suite-backed evidence.

\begin{table}[h]
  \centering
  \small
  \begin{tabular}{l l r}
    \hline

    \hline
    Curated feature suite           & frontend acceptance agrees with independent DTAL verifier & 28 / 28 pass            \\
    Local runtime cases             & semantic result matches expected exit/output behaviour    & 5 / 5 pass              \\

    \hline
  \end{tabular}

    current local and external benchmark corpora.}
  \label{tab:compiler-correctness-summary}
\end{table}

First, the feature suite provides evidence that representative source-language
programs compile successfully and agree with the independent verifier on
acceptance. The current curated feature-suite run records 28 out of 28 programs
as accepted by both the frontend and the physical DTAL verifier. This is
already a meaningful form of compiler-correctness evidence, because it shows
that programs exercising arrays, contracts, invariants, quantifiers, sortedness
reasoning, borrow discipline, and overflow-aware arithmetic survive lowering to
DTAL in a form the verifier still accepts. While this is not a behavioural
equivalence proof, it demonstrates that the compiler preserves the safety- and
proof-relevant structure needed by the verification architecture.

Second, the runtime and PolyBench-style suites provide semantic execution
evidence. For executable kernels, correctness is checked by exact outputs or
deterministic checksums rather than by process exit status alone. This is
important because a systems-language toolchain should be evaluated on whether it
computes the right result, not merely on whether it terminates. The current
expanded PolyBench-style corpus covers Floyd--Warshall, Jacobi-1D, Jacobi-2D,
Seidel-2D, MVT, ATAX, and GESUMMV, and all included kernels pass their defined
semantic checks against C baselines. This allows the chapter to make a narrow
but meaningful correctness claim: within the translated, committed benchmark
set, the compiler produces executable kernels whose observed outputs agree with
their baseline implementations.

This evidence should be interpreted with the right scope. The chapter can
credibly claim functional agreement on the curated local suite and the included
external kernels, and it can combine that with verifier agreement to support
the trust architecture. It cannot claim full compiler correctness in the
CompCert sense, nor should it imply that every possible future translation into
the Veritas fragment will automatically enjoy the same guarantee. The claim is
deliberately empirical, suite-bounded, and reproducible.

\subsection{Compiler and runtime practicality}

of the generated binaries. On the source-language side, the curated feature
suite provides a useful summary of compiler throughput. Table

\section{Source language expressiveness for verification}\label{sec:source-lang-eval}

The previous section evaluated Veritas as a toolchain that can compile and run
systems-oriented programs. This section shifts the focus back to the source
language as a verification-oriented language. The relevant question is not
only whether Veritas supports contracts and proofs in principle, but what
kinds of properties it can express in practice, how that compares with related
verification languages, and why the source-level expressiveness story is
different in Veritas because the resulting proof-relevant information is
preserved into DTAL rather than erased after frontend checking.

\subsection{Properties expressible in Veritas}

Within the supported fragment, Veritas can express a substantial set of the
properties typically expected from an SMT-backed verification language. The
curated feature suite covers preconditions and contract use, loop invariants,
bounded quantifiers, array bounds reasoning, arithmetic-safety conditions,
sortedness properties, and ownership-oriented borrow discipline. These are not
isolated one-feature examples: the representative programs in the suite
combine them in ways that require the compiler and verifier to preserve and
reuse facts across control flow, function calls, and memory operations. For
example, \texttt{21\_safe\_division} uses a proof-carrying precondition to
justify division, \texttt{20\_binary\_search} combines sortedness assumptions
with loop structure and symbolic arithmetic, \texttt{22\_bubble\_sort}
combines mutation with sortedness-oriented reasoning, and
\texttt{33\_mutable\_borrow} exercises exclusive-borrow discipline.

The breadth of this supported fragment is visible in the feature-suite
coverage data. Table~\ref{tab:veritas-feature-coverage} summarises a

non-trivial suite of array-heavy and proof-heavy programs rather than only
arithmetic toy examples.

\subsection{Comparison with verification-oriented languages}

The most appropriate comparison points are Dafny, Liquid Haskell, Verus, and
ATS. Dafny is the closest imperative SMT-backed verifier, Liquid Haskell is
the closest refinement-type automation baseline, Verus is the most relevant
modern systems-language verification comparison, and ATS is the clearest
historical predecessor for Veritas's broader goals. The key comparison is not
whether these languages all have ``verification features'' in the abstract,
but which safety properties and constraint classes they support naturally, and

This table sharpens the design-space comparison. At the source level, Veritas
is in a strong family rather than a unique one: Dafny, Liquid Haskell, Verus,
and ATS can all express substantial correctness and safety properties, even if
they differ in notation, automation, and programming model. It also makes the
current limits of Veritas clearer. The implemented fragment is strong on
array-heavy safety properties, arithmetic side conditions, contracts, and
borrow-aware reasoning, but weak on heap-shaped invariants, recursive proof
patterns, concurrency properties, and more protocol-oriented ghost-state
verification. Where Veritas starts to diverge is in the combination of
properties it supports naturally in an imperative, array-heavy fragment
together with the ability to preserve those checked constraints below the
source language.

Small matched examples make these stylistic differences clearer. The
\texttt{safe\_division} task from the comparison suite is expressed in Veritas
with a refinement-style argument type:

\begin{quote}
  \begin{verbatim}
fn safe_divide(a: int, b: {v: int | v != 0}) -> int {
    a / b
}
  \end{verbatim}
\end{quote}

Dafny phrases the same property as an imperative contract:

\begin{quote}
  \begin{verbatim}
method SafeDivide(a: int, b: int) returns (q: int)
  requires b != 0
  ensures q == a / b
{
  q := a / b;
}
  \end{verbatim}
\end{quote}

Verus uses Rust-flavoured contracts:

\begin{quote}
  \begin{verbatim}
fn safe_divide(a: int, b: int) -> (q: int)
    requires b != 0,
    ensures q == a / b,
{
    a / b
}
  \end{verbatim}
\end{quote}

ATS is stylistically different again, making the proof obligation an explicit
part of the function interface:

\begin{quote}
  \begin{verbatim}
fun safe_divide
  {b:int | b != 0}
  (a: int, b: int b): int = a / b
  \end{verbatim}
\end{quote}

These examples are enough to show the main stylistic split. Veritas, Dafny,
Liquid Haskell, and Verus all rely heavily on SMT-backed discharge once the
relevant specifications are present, though they package those specifications
differently. ATS is closer to a proof-oriented static programming discipline
in which rich types are central but the automation story is less
solver-driven.

The cross-system comparison suite currently contains four matched tasks:
preconditioned safe division, bounded array access, array initialisation with a
loop invariant, and binary search over a sorted collection. The precise
program text differs where necessary: Dafny uses heap arrays, Veritas and
Verus use fixed-size arrays naturally, and Liquid Haskell uses a more
functional representation. That is acceptable because the evaluation compares
the verified property rather than insisting on identical surface syntax. The
annotation-burden table for those four tasks is included in the appendix; it
shows Veritas to be competitive on this small suite, especially on the loop-
and search-heavy tasks.

This means the expressiveness comparison should not be read as a simple league
table. Veritas is not more expressive overall than Verus or F*, nor does it
match the ecosystem maturity of Dafny or Liquid Haskell. Its distinctive point
in the design space is narrower: it supports a useful SMT-verifiable
imperative fragment with contracts, arrays, invariants, quantifiers, and
borrow-aware reasoning, while also preserving enough of that information for
low-level re-checking.

\subsection{Source-level verification versus DTAL-level verification}

This last point is the most important distinction between Veritas and the
other verification-oriented languages considered here. Dafny, Liquid Haskell,
and Verus all perform their main verification work at the source level. Once a
program has passed the frontend verifier, the generated low-level artifact is
typically trusted to preserve the proved properties, modulo the trust placed in
the compiler and backend. Veritas, by contrast, is designed so that the
frontend does not have the last word: contracts, symbolic arithmetic facts,
bounds obligations, ownership operations, and block-entry states are preserved
into DTAL and re-checked there by an independent verifier.

This difference is not only architectural; it changes the interpretation of
the language's expressiveness. In most source-level verification systems, a
feature such as a loop invariant or array-bounds proof is an input to the
frontend verifier and then largely disappears from the compiled artifact. In
Veritas, the same proof obligation survives in a lower-level form that can
still fail if the compiler backend mishandles it. This is why the feature
suite and the DTAL tampering corpus belong to the same overall story: the
source language is expressive enough to specify interesting safety properties,
and the DTAL layer is expressive enough to preserve and independently re-check
them after lowering.

For the dissertation's design-space argument, this is the key result. Veritas
is not simply another refinement-typing frontend, nor simply another typed
assembly experiment. Its source-language expressiveness matters precisely
because it is carried below the source level into an independently verifiable
low-level representation.

\subsection{Interpreting Veritas's two-level verification cost}

The most important methodological point in this section is that Veritas incurs
two separable verification costs, whereas most related systems primarily incur
one. A source-level system such as Dafny or Liquid Haskell pays for checking
contracts, refinements, and invariants over the source program, and then
largely trusts the compiler to preserve those results. Veritas pays that same
kind of frontend proof-discharge cost, but can additionally pay for explicit
independent DTAL verification after lowering.

For that reason, two views of Veritas cost are both legitimate and both
necessary. The frontend-only view, approximated by \texttt{compile\_ms} and the
frontend SMT metrics, is the fairest comparison point against source-level
verification systems. The end-to-end view, measured by
\texttt{compile\_plus\_verify} wall-clock timings and \texttt{verify\_ms}, is
the right measure for evaluating the trust architecture that this dissertation
actually contributes. Using only the second view would make Veritas look
artificially expensive against systems that are solving a narrower problem;
using only the first view would hide the cost of the very mechanism that makes
Veritas distinctive.

The correct conclusion is therefore two-part. Relative to ordinary frontend
verification, Veritas's source-level costs are in the expected range for an
SMT-backed verifier on proof-heavy array programs. Relative to its own
architectural goals, the additional DTAL-level cost is measurable but
manageable, and it buys something the comparison systems do not attempt to
provide: a separately checkable low-level artifact that can reject backend
mistakes after source-level verification has already succeeded.

\section{Verifier functional correctness and reliability}\label{sec:verifier-correctness}

The previous sections evaluated expressiveness and cost. This section evaluates
the verifier itself as an independent checking mechanism. The relevant claim is
not that the verifier has been proved correct in a formal metatheoretic sense,
but that it behaves reliably in practice across four complementary dimensions:
agreement on valid programs, rejection of invalid source programs, rejection of
tampered low-level DTAL, and deterministic robustness on a small generated
corpus.

\subsection{Verifier agreement on valid programs}

The strongest positive evidence comes from the curated feature suite. For this
suite, the frontend compiler and the independent physical-DTAL verifier now
agree on acceptance for every frozen benchmark program. This matters because
the feature suite is not a collection of trivial smoke tests: it includes
arrays, contracts, loop invariants, quantifiers, safe arithmetic, sortedness
reasoning, and borrow-oriented examples. Agreement across that suite therefore
means that the low-level verifier accepts the same supported fragment that the
frontend is intended to accept.

agreement evidence.

\end{quote}

with

\begin{quote}
  \begin{verbatim}
mov v4, 1    : int(1)
  \end{verbatim}
\end{quote}

in a one-element shared-borrow dereference example, which turns a proven safe
access into a verifier-detected bounds failure. An ownership tamper can
replace an ownership-preserving path with an illegal duplicating move, for
example inserting

\begin{quote}
  \begin{verbatim}
mov v6, v1    : [int(7); 1]
  \end{verbatim}
\end{quote}

after a live borrow, which the verifier rejects as an ownership violation.
These mutations are intentionally small: the goal is to show that
safety-critical backend corruption need not be dramatic to be caught.

This evidence supports a narrow but important claim. It does not prove that
every possible semantic miscompilation is caught, nor that the compiler is
correct. What it does show is that representative low-level corruptions that
break the verifier's safety model are rejected even when the original source
program was valid. This is exactly the kind of evidence needed for the
untrusted-compiler story: safety-critical backend mistakes are not simply
trusted away once source-level verification has succeeded.

\subsection{Robustness evidence}

The final layer of reliability evidence comes from the fixed-seed robustness
track. This is not a benchmark suite and not a replacement for the curated
feature or negative suites. Instead, it asks whether the implementation
behaves deterministically and without crashes on a broader range of generated
small programs inside a restricted fragment.

The current robustness corpus contains 16 generated cases across four families:
valid arithmetic programs, valid array programs, invalid type errors, and
invalid syntax errors. The accompanying integration test checks three
properties:
deterministic compilation and DTAL generation for valid programs,
successful in-memory and text-DTAL verification for generated valid programs,
and deterministic failures with stable diagnostics for generated invalid
programs.

The current explicit run passes all three properties over the fixed corpus.
This does not say much about semantic completeness, but it does provide useful
engineering evidence that the implementation is stable under repeated
compilation and verification. It also already exposed a real bug during the
evaluation work: synthesized refinement names were previously allocated from a
global counter that was not reset between compilations, which made repeated
compilation of the same source produce drifting generated identifiers. Fixing
that issue improved both tool robustness and reproducibility of the DTAL
artifacts used elsewhere in the evaluation.

Taken together, these four evidence streams support a practical reliability
claim for the current implementation. The verifier agrees with the frontend on
the supported valid fragment, invalid programs are rejected across a broad
range of source-level failure classes, representative tampered low-level
artifacts are rejected after compilation, and the implementation behaves
deterministically on a fixed generated corpus. That is a substantially
stronger trust and reliability story than source-level acceptance alone.

\section{Trust architecture and trusted computing base}\label{sec:tcb-eval}

The earlier sections evaluated correctness, expressiveness, cost, and
reliability. This section turns back to the trust architecture itself. The
dissertation's claim is not only that Veritas can verify useful programs, but
that it does so with a trust boundary that is smaller and more explicit than a
conventional source-level verification pipeline. Emitted binary size is part of
the practicality discussion earlier in the chapter; here, code size matters
only indirectly, because Veritas emits compact freestanding binaries and does
not depend on a large trusted runtime. The main quantitative question is
therefore the size of the trusted implementation that remains on the verifier
side of the architecture.

\subsection{Trusted computing base analysis}

The more important quantitative result in this section is the trusted
computing base summary. In the current physical-DTAL architecture, the
compiler pipeline itself is intentionally untrusted: parser, frontend,
lowering, register allocation, code generation, and most surrounding
infrastructure are allowed to be buggy without directly invalidating the main
safety claim. What remains trusted is the verifier-side core together with the
underlying solver.

Table~\ref{tab:tcb-summary} gives the chapter-labelled size summary for that
trusted core.

This result should be interpreted carefully. It does not mean that the rest of
the implementation is unimportant, nor that the verifier is ``small'' in an
absolute sense. Nearly eight thousand lines of trusted verifier-side logic is
still a meaningful audit burden. The important point is relative rather than
absolute: only 18.4\% of the counted Rust implementation lies on the trusted
path for the core low-level safety claim, while 81.6\% of the implementation
is outside that path and may fail by being rejected rather than by silently
compromising safety.

This is where Veritas differs most sharply from source-level-only verification
systems. In a conventional architecture, once the frontend verifier has proved
the source program, the rest of the compiler backend is usually trusted to
preserve that result. In Veritas, the independent DTAL verifier removes much
of that backend from the trusted path by re-checking the low-level artifact
after lowering and register allocation. The quantitative TCB table therefore
does not only measure code size; it measures the practical payoff of the DTAL
architecture in trust-boundary terms.

The most accurate conclusion is therefore modest but strong. Veritas does not
yet deliver a tiny foundational checker in the style of a proof assistant
kernel, and the trusted verifier core is still a substantial engineering
artifact. But it does achieve a meaningful reduction in trust relative to the
whole implementation, and it does so in a way that is directly reflected in
the architecture and evaluation artifacts rather than only argued for
abstractly.

\section{Threats to validity and limitations}

No evaluation of a research prototype is complete without stating the limits of
the evidence explicitly. The results in this chapter are strong enough to
support the dissertation's main claims, but they are still constrained by the
current fragment, the current benchmark policy, and the current state of the
comparison infrastructure.

\subsection{Benchmark and corpus limitations}

The first limitation is that the main evaluation suites are curated rather than
exhaustive. This is a strength in methodological terms, because the suites are
frozen and reproducible, but it is also a limit on generality. The
\texttt{feature\_suite} provides broad coverage of the currently supported
fragment, yet that fragment is still strongest on fixed-size arrays, local
mutation, contracts, loop invariants, quantifiers, and borrow-oriented
examples. It is not strong evidence for heap-heavy data structures, arbitrary
pointer manipulation, concurrency, or a large module ecosystem, because those
lie outside the fragment currently evaluated.

The same applies to the external benchmarks. The PolyBench results use a
deliberately selected subset of kernels that fit the current Veritas language
and verifier without heroic rewriting. That is the right policy for a fair
evaluation, but it means that the PolyBench results are evidence for
structured numeric kernels rather than for arbitrary systems programs. Kernels
excluded by the suite policy should be interpreted as out of scope for the
current fragment, not silently reclassified as failures.

The DTAL tampering and robustness tracks are also intentionally bounded. The
tampering corpus covers representative low-level safety-critical mutations, not
all semantic miscompilations. The fixed-seed robustness corpus covers a small
generated fragment, not arbitrary valid or malformed Veritas and DTAL
programs. These are useful trust and engineering checks, but they should not
be mistaken for exhaustive fuzzing or full compiler validation.

\subsection{Cross-system comparison caveats}

The comparison with Dafny, Liquid Haskell, Verus, and ATS is informative, but
it also has clear comparability limits. These systems differ in host language,
programming model, proof style, and notion of what counts as a natural
encoding of a property. In the current comparison suite, Veritas and Verus use
fixed-size arrays naturally, Dafny uses heap arrays, and Liquid Haskell uses a
more functional representation with refinements or reflected predicates. This
is acceptable for comparing the verified property, but it weakens any claim of
perfect like-for-like syntactic or timing equivalence.

The cross-system timing comparison is also only partially complete at present.
The Veritas side of the comparison suite has been measured and validated
locally, and the Dafny, Liquid Haskell, and Verus programs are authored and
frozen, but those external toolchains were not available in the present
environment for fully controlled timing runs. The chapter therefore makes a
careful distinction between qualitative comparison, annotation-burden
comparison, and fully executed wall-clock comparison. This is a real empirical
limit and should be read as such.

Finally, even a completed wall-clock comparison would need careful
interpretation. Veritas incurs both source-level checking cost and optional
independent DTAL-level checking cost, whereas the other systems mainly incur
source-level verification cost. A direct timing comparison without that
distinction would be methodologically misleading.

\subsection{Current verifier and backend limitations}

The current implementation also has substantive technical limits. Veritas does
not yet aim to support the full design space of mature verification languages
or full systems languages. In particular, the evaluation does not claim strong
support for general heap allocation, pointer-rich APIs, concurrency-oriented
reasoning, large-scale modular verification, or proof patterns that rely on
heavier interactive theorem proving. These are not merely missing benchmarks;
they are areas where the language and verifier are not yet the right tool.

The verifier's reliability evidence should also be interpreted at the right
level. The feature suite, negative suite, tampering corpus, and robustness
track together show that the current implementation behaves coherently on the
supported fragment and catches representative backend corruption. They do not
constitute a formal proof of verifier soundness or completeness, nor do they
show that every possible incorrect but still type-shaped backend translation
would be rejected.

These limitations do not undermine the evaluation method. On the contrary, the
point of stating them explicitly is to keep the claims proportionate to the
implemented evidence. The chapter's strongest results are about a well-defined
fragment, a concrete trust architecture, and a reproducible set of suites and
artifacts. That is a narrower claim than ``general-purpose verified systems
language,'' but it is also a much better-supported one.

\section{Summary against project objectives}

Taken as a whole, the evaluation supports the dissertation's central claim:
Veritas is not merely a frontend refinement-type prototype, but a working
type-preserving compilation pipeline in which proof-relevant information is
preserved to a low-level representation and independently re-checked there. On
the frozen supported fragment, this architecture works in the intended sense.
The curated feature suite provides 28 out of 28 frontend/verifier agreements,
the curated negative suite provides 35 out of 35 rejections, the DTAL
tampering corpus shows that representative low-level corruptions are caught
after compilation, and the fixed-seed robustness track shows that the current
implementation behaves deterministically on a broader generated corpus.

Several objectives can therefore be treated as fully met. The project does
implement a DTAL-inspired trust architecture rather than only discussing one
conceptually. It does provide an independently operating verifier over the
compiled low-level artifact. It does support a non-trivial source-language
fragment including contracts, arrays, loop invariants, quantifiers,
sortedness-oriented reasoning, and borrow-aware examples. It also produces
real executable code and supports a meaningful external practicality story via
the translated PolyBench-style kernels.

Other objectives are best treated as partially met rather than fully complete.
The runtime and code-size results show that the compiler is usable and often
plausible, but not yet competitive with mature systems compilers on emitted
code quality. The verification-cost comparison with other languages is well
designed and partially instrumented, but not yet fully executed under one
local toolchain environment. The supported fragment is broad enough for a
strong dissertation argument, but still substantially narrower than a mature
systems language or a general-purpose verification platform.

The strongest overall conclusion is therefore architectural. Veritas occupies a
distinct and well-evidenced point in the design space between source-level
verification tools and foundational low-level proof systems. It combines
automated SMT-backed source reasoning with an independently checkable DTAL
layer, reducing the amount of compiler infrastructure that must be trusted for
the core safety claim. The main remaining limitations are not that this idea
fails, but that it has so far been demonstrated on a deliberately scoped
fragment rather than on the full range of systems-programming and verification
tasks. Within that scope, however, the evaluation shows the approach to be
successful, credible, and practically implemented.
