\section{Evaluation goals and methodology}
% no formalisation/proof of DTAL; does it successfully build on the foundation of xi and harper's DTAL (can their proofs be used as evidence/support here)?

This chapter evaluates the core goals of Veritas put forward in the proposal (Appendix [TODO]) and refined in the requirements analysis (Section~\ref{sec:requirements-anal}).
% The core memory-safety, control-flow safety and arithmetic safety properties Veritas aimed to support were array bounds checking, state consistency at joins and branches, function contract checking, and integer overflow. These features were fully realised in the implementation presented in Chapter~\ref{ch:impl} in addition to extensions that build on the core goals.

A central claim of Veritas' architecture is that low-level artifacts can be independently verified while the compiler can be untrusted. This was achieved owing to the refinement type system, verification-oriented language features, type-preserving compilation, as well as other components of the languages and compiler. Veritas also aimed to support a toolchain for a \emph{systems language}. This evaluation must therefore address several distinct questions:
\begin{itemize}
  \item Is the design and implementation of DTAL a useful realisation of the intended trust architecture?
  \item Are the source language and compiler implementations viable for a systems-language toolchain?
  \item Is the source language expressive enough for the targeted verification tasks?
  \item Is the additional cost imposed by independent DTAL-level verification practical enough to keep the toolchain usable?
  \item How confident can one be about the correctness of the verifier?
  \item What reduction in the TCB does Veritas achieve, and is that reduction substantial enough to justify the DTAL-based trust architecture?
\end{itemize}

\section{DTAL design and implementation}\label{sec:dtal-eval}

In the Veritas architecture, the target DTAL must be expressive enough to enable verification of the required safety properties.
% The Veritas DTAL implementation includes a subset of the features of Xi and Harper's DTAL for a narrower language but also extends the design in different directions.
% exploring ownership-aware memory operations, SMT-oriented refinement constraints, and verification of physically allocated code. 
The evaluation considers to what extent the DTAL implementation supports the intended trust architecture.
% rather than assessing it as a fully faithful formal engineering realisation of Xi and Harper's design.

\subsection{Relationship to Xi and Harper's DTAL}

Veritas is inspired directly by Xi and Harper's DTAL and preserves many of its central features and ideas most relevant for independent low-level verification. Shared features include:
% The shared structure is most clearly seen as a set of concrete mechanisms, each of which supports a corresponding safety property:
\begin{itemize}
  \item \textbf{Dependent block or label state.} This supports control-flow safety by ensuring that jumps and joins are only valid when the incoming machine state matches the target's expected typing context.
  \item \textbf{Singleton integer typing.} This supports arithmetic and indexing safety, since later instructions can rely on those symbolic facts when proving side conditions.
  \item \textbf{Size-indexed arrays.} This supports memory safety by making out-of-bounds reads and writes statically checkable.
  \item \textbf{Typed stack discipline.} This supports structural safety by preventing ill-typed stack use across calls, returns, and local temporaries.
  \item \textbf{Proof-relevant typed memory access.} This supports static memory-safety guarantees such as array-bound-check elimination.
\end{itemize}

It should be noted that Veritas narrows Xi and Harper's design in some directions. Xi and Harper's DTAL includes general tuple and array allocation primitives, existential dependent types in a broader form, and an extension for sum and tag reasoning. Veritas does not currently expose all of these as first-class DTAL features. Instead, it is more tightly focused on the subset of low-level facts needed for fixed-size arrays, arithmetic side conditions, contracts, and
borrow-aware source-language compilation. The logical fragment is chosen to match SMT-backed refinement checking, array bounds reasoning, and simple arithmetic safety properties rather than arbitrary proof terms.
% Safety evidence is represented operationally
%through constraints, singleton types, block entry states, assertions, and preconditions/postconditions, 
% rather than through the full richness of a foundational typed assembly formalism. 
This is a tradeoff where the implemented system sacrifices some theoretical generality in exchange for automation and a verification model that fits the rest of the toolchain. Given that the project's goal was not to recreate the full metatheory of Xi and Harper's DTAL, this is an appropriate restriction.
% Instead, the aim was to show the DTAL architecture could be used to move the trust boundary downwards and allow source-language facts to survive compilation in a form that is still checkable.

The most important continuity with Xi and Harper's DTAL lies in the independent low-level verification model
% which is enabled through the design of Veritas' DTAL. 
To demonstrate, below shows the Veritas version of the copy loop from Section~\ref{sec:dtal-background},
% This continuity can be seen directly in the instruction style. Xi and Harper's DTAL presents a copy loop using typed labels and register-indexed array access:
%
% \begin{quote}
%   \begin{verbatim}
% loop: {m:nat, n:nat | m <= n, i:nat}
% [r1: int array(m), r2: int array(n), r3: int(m), r4: int(i)]
% sub r5, r4, r3
% bgte r5, finish
% load r5, r1(r4)
% store r2(r4), r5
% \end{verbatim}
% \end{quote}
which preserves the same basic idea of typed labels and register-indexed array access, although the surface syntax is adapted to its implementation:

\begin{quote}
  \begin{verbatim}
.entry {v0: int}
.assume (v0 >= 0 && v0 < 4)
add v9, v0, v8    : {_synth_0: int | _synth_0 == (i + 1) }
.assert true
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}

The low-level program records sufficient information for the verifier to justify array access from the surrounding type and constraint context rather than relying on a dynamic bounds check.

\subsection{Extensions and deviations}

% Veritas also extends the design along axes that Xi and Harper's DTAL did not target.
% Notably, it adds ownership and borrowing operations,distinguishing shared borrows, mutable borrows, ownership transfer, and borrow termination. It also introduces a physical-DTAL layer, so that the verifier can operate after register allocation and instruction expansion rather than only on an idealised virtual assembly. 

Veritas preserves the same basic typed memory access idea, but also extends it with explicit refinement-carrying annotations that originate in source-level proof obligations, for example:
\begin{quote}
  \begin{verbatim}
div v2, v0, v1    : {_synth_0: int | _synth_0 == (a / b) }
load v10, [v1 + v9]    : int(7)
  \end{verbatim}
\end{quote}
% This illustrates that memory accesses are still justified by visible low-level constraints, but an arithmetic fact derived at the source-level has been preserved through lowering in symbolic SMT-friendly form. 
These carried obligations are re-checked by the verifier against the low-level code. This provides a broader source-to-low-level continuity for the particular fragment Veritas supports, including not just bounds facts but also contract-style and borrow-related safety obligations. Preserving additional proof-relevant annotations does increase the surface on which an untrusted compiler can introduce inconsistencies, and therefore may increase the risk of false rejection, but crucially, it does not expand the acceptance surface or weaken verification guarantees.
% However the added annotations also make backend mistakes visible to the independent verifier.
% , and this only expands the rejection surface rather than the acceptance surface.

Another extension is the introduction of explicit ownership and borrow-aware operations.
% Xi and Harper's DTAL was not designed around a Rust-like ownership discipline, whereas Veritas carries object ownership, shared borrows, mutable borrows, and borrow termination through DTAL as first-class phenomena. 
This extension pushes alias-control properties below the frontend where the relevant low-level operations are represented and re-checked in DTAL. This is a significant divergence from Xi and Harper's DTAL in order to serve a systems-language setting.

\begin{quote}
  \begin{verbatim}
alias_borrow v3, v1    : &[int(7); 1]
load v5, [v3 + v4]     : int
borrow_end v3          : &[int(7); 1]
  \end{verbatim}
\end{quote}

In this example, the creation, use, and termination of the borrowed view is represented explicitly in DTAL, which allows the verifier that the access occurs through a live borrow and that the borrow is ended consistently with the source-language ownership discipline.

Due to the architectural decision to perform verification after physical register allocation, Veritas defines a `physical DTAL' (the post-regalloc form of `virtual DTAL') with explicit scratch-register use, spills, prologues/epilogues, and instruction expansions. Xi and Harper's DTAL is most akin to Veritas' virtual DTAL as its semantics are given over an abstract machine, and register allocation and spill is explicitly not modelled in the language. The difference is visible in instructions such as:

\begin{quote}
  \begin{verbatim}
mov lr, r1    : int
cqo
idiv r7
mov r0, lr    : int
\end{verbatim}
\end{quote}

or in explicit stack and calling-convention machinery such as
\texttt{spill\_store}, \texttt{spill\_load}, \texttt{.prologue}, and
\texttt{.epilogue}.
% These do not make the language closer to the original paper's abstract presentation, but they do make it a stronger intermediate artifact for verifying the real backend pipeline that Veritas actually uses.
The main tradeoff of Veritas' architecture to support physical DTAL is complexity at the low level. Physical DTAL necessarily exposes register assignments, spill slots, calling-convention details, and instruction expansion that are absent from the source language. This makes the representation less elegant than an idealised typed assembly and increases the burden on the verifier. However, this design makes register allocation and instruction expansion part of the untrusted compiler, which is more useful for the project's trust model.

It does not model arbitrary heap structures, unrestricted pointers, concurrency, or the full range of low-level effects found in general systems code.
% These are not accidental omissions; they are part of the chosen scope that keeps the low-level verification story coherent and mechanically checkable.

\section{Veritas as a systems-language toolchain}\label{sec:veritas-sys-eval}

This section evaluates Veritas from the angle of a systems language toolchain. A core goal of the project was to apply the defined trust architecture in a systems-oriented context in order to address the challenges of upholding memory safety properties. This adds new requirements and expectations beyond those for independent low-level verification; systems languages commonly support imperative control flow, mutable state, pointers/references, and predictable data representation, while their compilers generate efficient native code and preserve the intended resource and safety behaviour of programs through the backend. While Veritas is currently far less mature than widely-used systems toolchains in language breadth, tooling, and ecosystem, the evaluation focuses on whether within the intended fragment, Veritas behaves like a plausible and pragmatic systems-language design which could be built on further.

% The previous section evaluated DTAL as a mechanism that supports the trust architecture. This section evaluates Veritas from the angle of a systems-language toolchain that happens to incorporate verification, rather than as a verification system that happens to emit code. This distinction matters because the project claims more than source-level proof automation. It claims to provide a small systems-oriented language that can compile to executable programs, support structured numeric kernels, and preserve safety relevant information through the backend. The evaluation therefore considers language-level systems features, compiler functional correctness, and the practical behaviour of the generated code.

\subsection{Systems-language feature comparison}

Compared with C and Rust, Veritas currently occupies an intermediate position. Like both languages, it supports first-order functions, mutable local state, fixed-size arrays, explicit integer reasoning, loop-based imperative control flow, and compilation to native code. Like Rust, it also has an ownership- and borrow-aware safety story rather than relying purely on unrestricted memory
manipulation. Unlike both, however, its design is centred around carrying verification-relevant information through the compilation pipeline. This makes Veritas less general-purpose than C or Rust as a production systems language, but also gives it a stronger explicit safety and trust architecture within its supported fragment.

\subsection{Compiler functional correctness}

The project aimed to deliver a compiler that is correct by following standard engineering principles. While the architecture treats the compiler as untrusted, a goal of the project was to show that the Veritas system developed has the potential to be usable as a systems language toolchain in itself. As it is not required that the compiler be formally proved to be semantically correct, the compiler's functional-correctness evaluation for whether it produces executable programs whose behaviour agrees with the intended semantics is empirical and corpus-based.

The first suite used for this purpose is the curated \texttt{feature\_suite}. This is the main local correctness corpus for the supported Veritas fragment: 28 programs chosen to cover arrays, mutable state, references and borrowing, preconditions, loop invariants, quantifiers, sortedness reasoning, safe division, and overflow-aware arithmetic. Its purpose is to check the compiler on representative source-language features and proof obligations. The current feature-suite results show all 28 programs accepted by both the frontend and the independent physical DTAL verifier, and passing
their runtime semantic checks. This demonstrates that, within the intended local fragment, the compiler preserves both the proof-relevant structure needed by the trust architecture and the executable behaviour of the compiled programs.

The second suite is the external PolyBench-style kernel suite. PolyBench/C is a widely used benchmark family for evaluating compilers and program-transformation systems on structured numeric kernels, especially in work on loop optimisation, polyhedral compilation, and high-performance array code. Its programs include small kernels with regular control flow, affine array indexing, and deterministic numeric behaviour, making them convenient for both performance and semantic comparison. Unlike the feature suite, whose role is to exercise the particular constructs and proof obligations that Veritas was built to support, the PolyBench-style suite provides a more objective external check on whether the compiler behaves correctly on recognised array- and loop-dominated workloads that are used outside this project.

Here the compile time is dominated much more by frontend SMT work than in the feature suite. This is because the kernel programs are dense in the forms of reasoning that Veritas discharges through SMT (repeated affine array indexing, nested loop structure, and arithmetic side conditions on statically bounded data), while the feature suite programs are broader in language coverage but less repetitive in proof-obligation structure.

\section{Source language expressiveness for verification}\label{sec:source-lang-eval}

This section focuses on the source language as a verification-oriented language. It evaluates what kinds of properties it can express in practice, how that compares with related verification languages, and why the source-level expressiveness story is different in Veritas because the resulting proof-relevant information is preserved into DTAL rather than erased after frontend checking.

\subsection{Properties expressible in Veritas}

Within the supported fragment, Veritas can express a substantial set of the properties typically expected from an SMT-backed verification language. In particular:
preconditions and postconditions, loop invariants, bounded quantified properties, array-bounds and arithmetic safety conditions, sortedness-style functional properties, and ownership-oriented borrowing constraints.

repeated here at length.

\subsection{Interpreting Veritas's two-level verification cost}

The most important methodological point in this section is that Veritas incurs
two separable verification costs, whereas most related systems primarily incur
one. A source-level system such as Dafny or Liquid Haskell pays for checking
contracts, refinements, and invariants over the source program, and then
largely trusts the compiler to preserve those results. Veritas pays that same
kind of frontend proof-discharge cost, but can additionally pay for explicit
independent DTAL verification after lowering.

For that reason, two views of Veritas cost are both legitimate and both
necessary. The frontend-only view, approximated by \texttt{compile\_ms} and the
frontend SMT metrics, is the fairest comparison point against source-level
verification systems. The end-to-end view, measured by
\texttt{compile\_plus\_verify} wall-clock timings and \texttt{verify\_ms}, is
the right measure for evaluating the trust architecture that this dissertation
actually contributes. Using only the second view would make Veritas look
artificially expensive against systems that are solving a narrower problem;
using only the first view would hide the cost of the very mechanism that makes
Veritas distinctive.

The correct conclusion is therefore two-part. Relative to ordinary frontend
verification, Veritas's source-level costs are in the expected range for an
SMT-backed verifier on proof-heavy array programs. Relative to its own
architectural goals, the additional DTAL-level cost is measurable but
manageable, and it buys something the comparison systems do not attempt to
provide: a separately checkable low-level artifact that can reject backend
mistakes after source-level verification has already succeeded.

\section{Verifier functional correctness and reliability}\label{sec:verifier-correctness}

The previous sections evaluated expressiveness and cost. This section evaluates
the verifier itself as an independent checking mechanism. The relevant claim is
not that the verifier has been proved correct in a formal metatheoretic sense,
but that it behaves reliably in practice across four complementary dimensions:
agreement on valid programs, rejection of invalid source programs, rejection of
tampered low-level DTAL, and deterministic robustness on a small generated
corpus.

\subsection{Verifier agreement on valid programs}

The strongest positive evidence comes from the curated feature suite. For this
suite, the frontend compiler and the independent physical-DTAL verifier now
agree on acceptance for every frozen benchmark program. This matters because
the feature suite is not a collection of trivial smoke tests: it includes
arrays, contracts, loop invariants, quantifiers, safe arithmetic, sortedness
reasoning, and borrow-oriented examples. Agreement across that suite therefore
means that the low-level verifier accepts the same supported fragment that the
frontend is intended to accept.

agreement evidence.

agreement story once they have been stabilised and explicitly added to frozen
manifests.

\subsection{Rejection of tampered DTAL}

The most distinctive reliability evidence is the DTAL tampering corpus, since
it tests the trust boundary directly rather than only the source language. In
this corpus, a valid curated source program is compiled to DTAL, the baseline
DTAL is verified successfully, and then a small syntax-preserving mutation is
applied to the low-level program. The verifier is expected to reject the
tampered DTAL.

The current corpus contains 14 cases spanning:
return-signature mismatches, strengthened preconditions, contradictory
assertions, positive and negative out-of-bounds accesses, arithmetic overflow,
use-after-drop, ownership duplication, mutable-aliasing violations, and entry
state or signature mismatches. Table~\ref{tab:dtal-tampering-summary}
summarises these mutation families.

Three short examples make the corpus more concrete. A structural tamper can be
as small as changing the declared return type of a function from the valid
baseline

\begin{quote}
  \begin{verbatim}
.returns int
  \end{verbatim}
\end{quote}

to the mutated form

\begin{quote}
  \begin{verbatim}
.returns bool
  \end{verbatim}
\end{quote}

which the verifier rejects as a return-type mismatch. A bounds-safety tamper
can change an in-bounds index into an invalid one, for example replacing

\begin{quote}
  \begin{verbatim}
mov v4, 0    : int
  \end{verbatim}
\end{quote}

with

\begin{quote}
  \begin{verbatim}
mov v4, 1    : int(1)
  \end{verbatim}
\end{quote}

in a one-element shared-borrow dereference example, which turns a proven safe
access into a verifier-detected bounds failure. An ownership tamper can
replace an ownership-preserving path with an illegal duplicating move, for
example inserting

\begin{quote}
  \begin{verbatim}
mov v6, v1    : [int(7); 1]
  \end{verbatim}
\end{quote}

after a live borrow, which the verifier rejects as an ownership violation.
These mutations are intentionally small: the goal is to show that
safety-critical backend corruption need not be dramatic to be caught.

This evidence supports a narrow but important claim. It does not prove that
every possible semantic miscompilation is caught, nor that the compiler is
correct. What it does show is that representative low-level corruptions that
break the verifier's safety model are rejected even when the original source
program was valid. This is exactly the kind of evidence needed for the
untrusted-compiler story: safety-critical backend mistakes are not simply
trusted away once source-level verification has succeeded.

\subsection{Robustness evidence}

The final layer of reliability evidence comes from the fixed-seed robustness
track. This is not a benchmark suite and not a replacement for the curated
feature or negative suites. Instead, it asks whether the implementation
behaves deterministically and without crashes on a broader range of generated
small programs inside a restricted fragment.

The current robustness corpus contains 16 generated cases across four families:
valid arithmetic programs, valid array programs, invalid type errors, and
invalid syntax errors. The accompanying integration test checks three
properties:
deterministic compilation and DTAL generation for valid programs,
successful in-memory and text-DTAL verification for generated valid programs,
and deterministic failures with stable diagnostics for generated invalid
programs.

The current explicit run passes all three properties over the fixed corpus.
This does not say much about semantic completeness, but it does provide useful
engineering evidence that the implementation is stable under repeated
compilation and verification. It also already exposed a real bug during the
evaluation work: synthesized refinement names were previously allocated from a
global counter that was not reset between compilations, which made repeated
compilation of the same source produce drifting generated identifiers. Fixing
that issue improved both tool robustness and reproducibility of the DTAL
artifacts used elsewhere in the evaluation.

Taken together, these four evidence streams support a practical reliability
claim for the current implementation. The verifier agrees with the frontend on
the supported valid fragment, invalid programs are rejected across a broad
range of source-level failure classes, representative tampered low-level
artifacts are rejected after compilation, and the implementation behaves
deterministically on a fixed generated corpus. That is a substantially
stronger trust and reliability story than source-level acceptance alone.

\section{Trust architecture and trusted computing base}\label{sec:tcb-eval}

The earlier sections evaluated correctness, expressiveness, cost, and
reliability. This section turns back to the trust architecture itself. The
dissertation's claim is not only that Veritas can verify useful programs, but
that it does so with a trust boundary that is smaller and more explicit than a
conventional source-level verification pipeline. Emitted binary size is part of
the practicality discussion earlier in the chapter; here, code size matters
only indirectly, because Veritas emits compact freestanding binaries and does
not depend on a large trusted runtime. The main quantitative question is
therefore the size of the trusted implementation that remains on the verifier
side of the architecture.

\subsection{Trusted computing base analysis}

The more important quantitative result in this section is the trusted
computing base summary. In the current physical-DTAL architecture, the
compiler pipeline itself is intentionally untrusted: parser, frontend,
lowering, register allocation, code generation, and most surrounding
infrastructure are allowed to be buggy without directly invalidating the main
safety claim. What remains trusted is the verifier-side core together with the
underlying solver.

Table~\ref{tab:tcb-summary} gives the chapter-labelled size summary for that
trusted core.

\begin{table}[h]
  \centering
  \small
  \begin{tabular}{l r r r}
    \hline
    \textbf{Trusted component} & \textbf{Trusted lines} & \textbf{Total lines} & \textbf{Trusted ratio} \\
    \hline
    \texttt{verifier\_tcb}     & 7864                   & 42775                & 0.184                  \\
    \hline
  \end{tabular}
  \caption{Trusted computing base size for the current Veritas implementation.}
  \label{tab:tcb-summary}
\end{table}

This result should be interpreted carefully. It does not mean that the rest of
the implementation is unimportant, nor that the verifier is ``small'' in an
absolute sense. Nearly eight thousand lines of trusted verifier-side logic is
still a meaningful audit burden. The important point is relative rather than
absolute: only 18.4\% of the counted Rust implementation lies on the trusted
path for the core low-level safety claim, while 81.6\% of the implementation
is outside that path and may fail by being rejected rather than by silently
compromising safety.

This is where Veritas differs most sharply from source-level-only verification
systems. In a conventional architecture, once the frontend verifier has proved
the source program, the rest of the compiler backend is usually trusted to
preserve that result. In Veritas, the independent DTAL verifier removes much
of that backend from the trusted path by re-checking the low-level artifact
after lowering and register allocation. The quantitative TCB table therefore
does not only measure code size; it measures the practical payoff of the DTAL
architecture in trust-boundary terms.

The most accurate conclusion is therefore modest but strong. Veritas does not
yet deliver a tiny foundational checker in the style of a proof assistant
kernel, and the trusted verifier core is still a substantial engineering
artifact. But it does achieve a meaningful reduction in trust relative to the
whole implementation, and it does so in a way that is directly reflected in
the architecture and evaluation artifacts rather than only argued for
abstractly.

\section{Summary against project objectives}

Taken as a whole, the evaluation supports the dissertation's central claim:
Veritas is not merely a frontend refinement-type prototype, but a working
type-preserving compilation pipeline in which proof-relevant information is
preserved to a low-level representation and independently re-checked there. On
the frozen supported fragment, this architecture works in the intended sense.
The curated feature suite provides 28 out of 28 frontend/verifier agreements,
the curated negative suite provides 35 out of 35 rejections, the DTAL
tampering corpus shows that representative low-level corruptions are caught
after compilation, and the fixed-seed robustness track shows that the current
implementation behaves deterministically on a broader generated corpus.

Several objectives can therefore be treated as fully met. The project does
implement a DTAL-inspired trust architecture rather than only discussing one
conceptually. It does provide an independently operating verifier over the
compiled low-level artifact. It does support a non-trivial source-language
fragment including contracts, arrays, loop invariants, quantifiers,
sortedness-oriented reasoning, and borrow-aware examples. It also produces
real executable code and supports a meaningful external practicality story via
the translated PolyBench-style kernels.

Other objectives are best treated as partially met rather than fully complete.
The runtime and code-size results show that the compiler is usable and often
plausible, but not yet competitive with mature systems compilers on emitted
code quality. The verification-cost comparison with other languages is well
designed and partially instrumented, but not yet fully executed under one
local toolchain environment. The supported fragment is broad enough for a
strong dissertation argument, but still substantially narrower than a mature
systems language or a general-purpose verification platform.

The strongest overall conclusion is therefore architectural. Veritas occupies a
distinct and well-evidenced point in the design space between source-level
verification tools and foundational low-level proof systems. It combines
automated SMT-backed source reasoning with an independently checkable DTAL
layer, reducing the amount of compiler infrastructure that must be trusted for
the core safety claim. The main remaining limitations are not that this idea
fails, but that it has so far been demonstrated on a deliberately scoped
fragment rather than on the full range of systems-programming and verification
tasks. Within that scope, however, the evaluation shows the approach to be
successful, credible, and practically implemented.
