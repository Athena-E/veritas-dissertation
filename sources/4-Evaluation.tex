\section{Qualitative analysis}\label{sec:qualitative-analysis}

\subsection{DTAL design and implementation}\label{sec:dtal-eval}

In the Veritas architecture, DTAL must be expressive enough to carry the facts needed for independent low-level checking. The evaluation therefore considers whether the implemented DTAL supports the intended trust architecture, rather than whether it is a complete reimplementation of Xi and Harper's formal system.

\subsubsection{Relationship to Xi and Harper's DTAL}

Veritas is inspired directly by Xi and Harper's DTAL and preserves the mechanisms most relevant to independent low-level verification:
\begin{itemize}
  \item \textbf{Dependent block or label state.} This supports control-flow safety by ensuring that jumps and joins are only valid when the incoming machine state matches the target's expected typing context.
  \item \textbf{Singleton integer typing.} This supports arithmetic and indexing safety, since later instructions can rely on those symbolic facts when proving side conditions.
  \item \textbf{Size-indexed arrays.} This supports memory safety by making out-of-bounds reads and writes statically checkable.
  \item \textbf{Typed stack discipline.} This supports structural safety by preventing ill-typed stack use across calls, returns, and local temporaries.
  \item \textbf{Proof-relevant typed memory access.} This supports static memory-safety guarantees such as array-bound-check elimination.
\end{itemize}

Veritas narrows the original design in several directions. Xi and Harper's DTAL includes general tuple and array allocation primitives, existential dependent types in a broader form, and an extension for sum and tag reasoning. Veritas instead focuses on the low-level facts needed for fixed-size arrays, arithmetic side conditions, contracts, and borrow-aware compilation. This sacrifices some theoretical generality in exchange for automation and a logical fragment that fits SMT-backed checking.

The important continuity is the independent low-level verification model. The Veritas version of the copy-loop style example from Section~\ref{sec:dtal-background} uses different syntax, but still records block assumptions, symbolic arithmetic, and a typed memory access in the low-level artifact itself:

\begin{quote}
  \begin{verbatim}
.entry {v0: int}
.assume (v0 >= 0 && v0 < 4)
add v9, v0, v8    : {_synth_0: int | _synth_0 == (i + 1) }
.assert true
load v10, [v1 + v9]    : int(7)
\end{verbatim}
\end{quote}

The verifier can therefore justify the array access from the DTAL type and constraint context rather than relying on a dynamic bounds check or on the compiler's internal reasoning.

\subsubsection{Extensions and deviations}

Veritas also extends DTAL in directions not targeted by Xi and Harper. First, source-level obligations survive lowering as explicit low-level refinements:
\begin{quote}
  \begin{verbatim}
div v2, v0, v1    : {_synth_0: int | _synth_0 == (a / b) }
load v10, [v1 + v9]    : int(7)
  \end{verbatim}
\end{quote}
These obligations are not trusted as compiler-issued certificates; they are re-checked by the verifier against the emitted low-level code. This provides broader source-to-low-level continuity for the fragment Veritas supports, including bounds facts, contract-style obligations, and borrow-related safety constraints. Carrying more annotations gives an untrusted compiler more ways to emit inconsistent DTAL, but this increases the risk of false rejection rather than false acceptance.

Second, Veritas adds explicit ownership and borrow-aware operations. This pushes alias-control properties below the frontend, so that creation, use, and termination of borrows are represented and re-checked in DTAL:

\begin{quote}
  \begin{verbatim}
alias_borrow v3, v1    : &[int(7); 1]
load v5, [v3 + v4]     : int
borrow_end v3          : &[int(7); 1]
  \end{verbatim}
\end{quote}

Here, \texttt{alias\_borrow} creates the shared borrowed view \texttt{v3}, the \texttt{load} uses that view, and \texttt{borrow\_end} terminates it. The verifier checks that the access occurs through a live borrow and that the borrow is ended consistently with the source-language ownership discipline.

Finally, Veritas introduces a physical DTAL stage after register allocation. Xi and Harper's DTAL is closest to Veritas' virtual DTAL: an abstract typed assembly before register allocation and spill. Physical DTAL instead exposes scratch-register use, spills, prologues/epilogues, and instruction expansions:

\begin{quote}
  \begin{verbatim}
mov lr, r1    : int
cqo
idiv r7
mov r0, lr    : int
\end{verbatim}
\end{quote}

or in explicit stack and calling-convention machinery such as
\texttt{spill\_store}, \texttt{spill\_load}, \texttt{.prologue}, and
\texttt{.epilogue}.
This makes DTAL less elegant than the idealised presentation, but it moves more backend work outside the trusted path. Register allocation and instruction expansion become part of the untrusted compiler because their results are still checked before final encoding.

\subsection{Veritas as a systems-language toolchain}\label{sec:veritas-sys-eval}

This subsection evaluates whether Veritas has enough systems-language structure to make the later compiler and runtime measurements meaningful. The comparison is deliberately scoped: Veritas is not a mature C/Rust competitor, but it should support enough low-level imperative programming to justify evaluation as a small verified systems-language toolchain.

\subsubsection{Systems-language feature comparison}

Compared with C and Rust, Veritas currently occupies an intermediate position. Like both languages, it supports first-order functions, mutable local state, fixed-size arrays, explicit integer reasoning, loop-based imperative control flow, and compilation to native code. Like Rust, it also has an ownership- and borrow-aware safety story rather than relying purely on unrestricted memory
manipulation. Unlike both, however, its design is centred around carrying verification-relevant information through the compilation pipeline. This makes Veritas less general-purpose than C or Rust as a production systems language, but also gives it a stronger explicit safety and trust architecture within its supported fragment.

\subsection{Source language expressiveness for verification}\label{sec:source-lang-eval}

This subsection evaluates Veritas as a verification-oriented source language: what properties it can express, how that compares with related languages, and where the current fragment stops.

\subsubsection{Properties expressible in Veritas}

Within the supported fragment, Veritas can express the properties central to this project: preconditions and postconditions, loop invariants, bounded quantified properties, array-bounds and arithmetic safety conditions, sortedness-style functional properties, and ownership-oriented borrowing constraints.

This is sufficient for the dissertation's array-heavy and proof-heavy examples, but not for the full range of properties supported by mature verification ecosystems.

\section{Quantitative analysis}\label{sec:quantitative-analysis}

\subsection{Compiler functional correctness}

The project aimed to deliver a compiler that is correct by following standard engineering principles. While the architecture treats the compiler as untrusted, a goal of the project was to show that the Veritas system developed has the potential to be usable as a systems language toolchain in itself. As it is not required that the compiler be formally proved to be semantically correct, the compiler's functional-correctness evaluation for whether it produces executable programs whose behaviour agrees with the intended semantics is empirical and corpus-based.

All 28 programs of the \texttt{feature\_suite} are accepted by the compiler frontend and passes runtime semantic checks. This demonstrates that, within the intended local fragment, the compiler preserves both the proof-relevant structure needed by the trust architecture and the executable behaviour of the compiled programs.

All seven PolyBench kernels pass their defined semantic checks. Correctness was evaluated by deterministic checksum agreement (of the final array or result state of programs) against C baselines.

While these results do not amount to full compiler correctness in the CompCert sense, nor does it imply that every future program in the Veritas fragment will automatically enjoy the same guarantee, it supports a strong suite-bounded claim: for the representative local feature corpus and the committed external kernel corpus, the delivered compiler both preserves verifier-relevant structure and produces binaries whose observed behaviour matches the intended semantics.

Among them, Jacobi-2D and Seidel-2D are the most stable qualitatively: their relative separation from GCC remains in a fairly narrow band as the problem size grows, suggesting a persistent overhead on stencil-style 2D kernels rather than a one-off anomaly. Floyd--Warshall also remains slower throughout, but with a noticeably wider spread across sizes, which suggests that its dynamic-programming update pattern is more sensitive to backend code shape and memory behaviour.

The lighter matrix/vector kernels remain much closer to the C
baselines. GESUMMV stays near parity across the sweep and is below GCC
\texttt{-O3} at the smallest point, while MVT is near or below GCC for the smaller sizes but moves above it at the larger points. This is a useful counterpoint to the stencil kernels: Veritas does not incur one uniform slowdown on all array-heavy programs, and the relative runtime cost depends strongly on the computational pattern being compiled.

The experiments show that the checked-C baseline does not behave as a simple constant penalty. For some kernels and sizes it is close to the unchecked GCC baseline, while in others it is modestly slower or occasionally slightly faster. The scaling sweep therefore supports the interpretation that explicit dynamic checks do not produce one uniform overhead, and short-kernel behaviour can be affected by code shape as well as by the checks themselves. The explicit checks also change the generated code shape, which can affect register allocation, scheduling, cache state etc., and on short-running kernels these code-generation differences, together with typical benchmark noise, can outweigh the nominal cost of the added checks.

The results of the experiment support the conclusion that the generated code is executable, semantically validated, and often within a small constant factor of compiled C on the tested kernels, while also participating in a verification pipeline that C itself does not provide. \subsection{Verification cost and performance}\label{sec:verification-perf}

This section asks the question of verification cost: how expensive is it to check those properties, where in the pipeline that cost appears, and how Veritas should be compared fairly with source-level verification systems that do not also perform an explicit low-level re-checking stage.

\subsubsection{Veritas verification cost breakdown}

The first layer of cost evidence comes from the curated feature suite. These results separate source-to-DTAL compilation cost from the explicit DTAL verification stage. Across the current 28-program suite, mean source-to-DTAL compilation time is 27.110\,ms, mean explicit DTAL verification time is 9.116\,ms, mean frontend SMT time is 13.097\,ms, and mean verifier SMT time is 8.737\,ms. The worst case on both compile and explicit verification cost is \texttt{binary\_search}, at 163.817\,ms and 55.209\,ms respectively.
For the current supported fragment, the mean explicit verifier cost is materially smaller than the mean frontend source-to-DTAL cost. The extra low-level checking stage is an additional cost, but not one that dominates the overall pipeline uniformly. The most expensive programs are exactly the ones that combine several proof mechanisms at once: binary search is heavy because it mixes loop invariants, symbolic arithmetic, and sortedness-oriented reasoning, while the
simpler contract and borrow examples remain much cheaper.

\subsection{Trust architecture and trusted computing base}\label{sec:tcb-eval}

This section returns to the dissertation's architectural claim: Veritas should not only verify useful programs, but do so with a smaller and more explicit trust boundary than a source-level-only verification pipeline.
